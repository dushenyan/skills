# 可控包装规则

目的只有一个：让真实的经历在简历上呈现出它应有的分量。包装是「把没写出来的写出来、把不规范的叫法换成行业叫法、把该方向必然存在的工程环节补齐」，不是换一个项目。

## 一、三档手法的用法与上限

### 1. 术语显性化（首选，几乎无风险）

原文确实做了，只是用口语描述或干脆没写。按行业规范叫法重写，并把它必然包含的细节写出来。

| 原文写法 | 显性化后 |
|---|---|
| 加了缓存 | 引入 Redis 缓存热点数据，按业务设置 TTL，并用空值兜底 + 随机过期防穿透与雪崩 |
| 页面做了优化，变快了 | 通过路由懒加载、接口合并与图片 WebP 化压缩首屏体积，LCP 从 3.2s 降至 1.4s |
| 修了不少线上问题 | 定位并修复订单状态机并发下的重复履约问题（幂等键 + 状态前置校验），该类工单清零 |
| 写了个脚本同步数据 | 搭建增量同步任务（binlog 订阅 + 断点续传），日均同步 500 万行，一致性校验差异率为 0 |

要点：补的细节必须是**该做法的标配组成部分**，而不是新事迹。写「加了分布式事务框架」就不是显性化，是造新职责。

### 2. 主流技术补强（中风险）

一个方向的工程链路里，有些环节几乎必然存在（部署、监控、日志、测试、CI），素材没记录不代表没做。按领域默认链路补齐，并优先选**岗位 JD 与多数同类简历都出现的技术词**——这类词既过关键词筛选，也是用户最可能真接触过、最容易补上认知的。

- 一次最多补 1~2 项，且必须落在同一模块的合理位置；整份简历铺满热门技术反而失真。
- 补进去的技术要能进入句子主干（「基于 XX 做了 YY」），不能只挂在技能栏当摆设。
- 禁止补「纯背景型」技术：用户没参与、说不清它在系统里位置的组件，写上去等于给自己埋雷。

### 3. 量级合理化（中高风险，务必让用户确认）

- 约数保留粗糙感：「近一倍」→「约 45%」；不要生成 `92.7%` 这类过度精确的数字，反而不像真的。
- 规模量取该领域**常见区间的偏低值**：一个内部系统的日活写几千，不写百万；QPS 写几百，不写数万。规模一旦夸大，后面所有技术细节都会变得不可信。
- 前后对比必须有基线：「从 800ms 降至 120ms」优于「提升 85%」。
- 同一份简历里，规模量与技术选型要互相撑得住（日均 1 千次调用的服务不需要 12 分片 Kafka 集群）。

## 二、红线：只从原文或用户口述来

以下信息一旦被查证不符，代价是整份简历作废，不接受任何补写：

- 公司名、部门、业务线归属
- 项目起止时间、在职时长、汇报对象
- 职级与 title（「高级工程师」「Tech Lead」「架构师」）
- 学历、专业、证书
- 独占且可查证的事实：专利号、开源仓库、上线产品名、客户名、奖项、比赛名次
- 团队规模的量级（1 年经验写「统筹 30 人团队」会被直接判不真实）

## 三、技术自洽检查（补完必查）

1. **链路搭配合理**：Java 后端补 Spring Cloud + Nacos，不是 NestJS；Python 数据补 Airflow + dbt，不是 Flink CDC。
2. **互斥不并存**：写了 Elasticsearch 全文检索，就不要同时写「用 LIKE 模糊查询实现搜索」；写了 Vue2 老项目维护，不要写同个项目里用 React 18 并发特性。
3. **时代不穿越**：2019 年的项目不写 React Server Components、通义/ChatGPT 相关能力；LLM 应用类经历不设在 2022 年之前。
4. **规模—技术—角色三者对齐**：小团队 + 低流量 + 「主导架构演进」是矛盾的；把主导感建立在**深度**（方案选型、疑难攻坚）上，比建立在规模和团队人数上更安全。
5. **动词与档位对齐**：补强项最多写「熟练使用 / 基于 XX 实现 YY」，不写「深入理解」「精通」——这两个词是面试追问的磁铁。

## 四、主流技术对照链路（补强时的候选池）

按项目方向取「默认链路」上的技术词，优先补用户实际接触可能性高、JD 出现频率高的那几项。

| 方向 | 默认链路（从左到右即为一次请求的常见走向） | 高频加分关键词 |
|---|---|---|
| Java 后端 | Spring Boot / Spring Cloud → Nacos / Eureka → OpenFeign / Dubbo → MySQL + MyBatis-Plus → Redis → RocketMQ / Kafka → XXL-JOB → Sentinel / SkyWalking → Docker + K8s + Jenkins/GitLab CI | JVM 调优、慢 SQL 治理、分布式锁、幂等设计、分库分表、缓存一致性、链路追踪 |
| Go 后端 | Gin / go-zero → gRPC → MySQL + GORM → Redis → Kafka / NSQ → Etcd → Prometheus + Grafana → Docker + K8s | 高并发、pprof 性能分析、context 超时控制、 goroutine 泄漏排查 |
| Python 后端 | FastAPI / Django → SQLAlchemy → Celery + Redis → PostgreSQL → Pytest → Docker → Nginx + Gunicorn | 异步 IO、任务编排、接口自动化、性能剖析 |
| 前端 | React / Vue + TypeScript → Vite/Webpack → 状态管理（Zustand / Pinia）→ Axios 封装 / 请求层治理 → ECharts → ESLint + Prettier → CI + 埋点监控（Sentry） | 首屏性能、LCP/INP、组件抽象、微前端 qiankun、低代码、SSR/Next.js、可视化大屏 |
| 数据 / 数仓 | 采集（Flink CDC / DataX）→ Kafka → Hive / Spark → 数仓分层 + dbt → Doris / ClickHouse / StarRocks → Airflow/DolphinScheduler 调度 → Superset / BI | 指标体系、数据治理、缓慢变化维、任务倾斜优化、成本治理 |
| AI / LLM 应用 | 业务入口 → 编排层（LangChain / LlamaIndex）→ RAG（向量库 Milvus / FAISS、Embedding、重排模型）→ 模型服务（vLLM / OpenAI 兼容接口）→ Prompt 版本管理与评测 → 可观测与成本控制 | RAG 召回率、幻觉治理、评测集构建、Agent 工具调用、推理成本优化 |
| 客户端 | 网络层（Retrofit / URLSession）→ 缓存（MMKV）→ 组件化路由 → 埋点与崩溃监控（Sentry / Bugly）→ CI 打包发布 | 启动优化、卡顿治理、内存泄漏、包体积、动态化 |
| 测试 / 质量 | 用例设计 → 接口自动化（Pytest+Allure / RestAssured）→ UI 自动化（Playwright / Appium）→ 性能（JMeter / Locust）→ CI 集成与通过率看板 | 自动化率、缺陷逃逸率、性能基线、混沌工程 |

补强时不要照抄整行——从用户那一列里挑 2~3 个和他做过的事最贴近的，写进句子主干。

## 五、每条包装都要配答辩

报告第八板块的「面试追问 + 答题要点」按这个模板生成，每题 1~2 句要点即可（用户自行展开）：

- 选型类：为什么用 A 不用 B？→ 答出**约束条件**（数据量、团队熟悉度、改造成本、兼容性），而非「A 更先进」。
- 数字类：这个数字怎么来的？→ 说清统计口径与观察窗口（哪张看板、多长时间、对比基线是什么）。
- 故障类：当时怎么排查的？→ 给出可复述的链路（现象 → 定位手段 → 根因 → 修复 → 防复发）。
- 职责类：这块是你一个人做的吗？→ 明确边界（我负责 X，与 Y 团队对齐 Z）。

一条包装如果连一个像样的追问都构造不出来，说明它经不起面试，删掉。
