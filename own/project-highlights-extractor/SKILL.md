# 项目要点萃取与简历包装

把用户提供的项目素材加工成一份「简历可直接粘贴」的报告：既萃取已有事实，也在事实的延长线上做**可控包装**——补上该领域主流技术、把做了但没写的事说清楚、把模糊的量级合理化。目标只有一个：让这份经历在简历上好看、在面试里答得住。

定稿前必须走「终检：去 AI 味」，见本文同名章节。

## 适用输入

- 项目复盘、工作总结、周报/月报、述职材料
- 技术方案、设计文档、README、会议纪要、面试点整理
- 聊天记录、便签、口述整理稿；甚至只有一两句话的薄素材
- 单文件、多文件、直接粘贴文本均可；文件较多时先全部读完再动笔

---

## 一、铁律（先于一切技巧）

1. **可以充实，但必须分档标记。** 报告里每条内容属于且只属于一档：`事实`（原文明示）、`推断`（由线索合理推导）、`包装`（为呈现效果补写）。后两档必须显式标记，用户才知道哪里要准备答辩。
2. **不偏离方向。** 包装前先锚定一句话：「这个项目真实的核心方向是什么」。所有补写必须挂在这条线上——强化该方向的岗位画像，而不是炫技。前端经历不补 Kafka 调优。
3. **主流优先，不猎奇。** 补技术时选该领域**默认链路**上的主流方案（多数面试官和候选人都熟悉），命中关键词筛选即可，不为显得高级而堆小众组件。
4. **可答辩是底线。** 每条包装内容必须能通过三层追问：做了什么 → 为什么这么选 → 踩了什么坑/权衡了什么。答不出三层的，删掉或降级表述。
5. **红线不碰**：公司名、起止时间、职级 title、学历、汇报关系，以及专利号、开源仓库、客户名等一查就穿的独占性事实，只能来自原文或用户口述，不代填。

## 二、执行流程

### 第 1 步：收齐素材并锚定方向

- 确认素材清单：有哪些文件、各是什么类型、覆盖项目哪个阶段；全部通读后再动笔，禁止读到一半就输出。
- 若用户提供了**目标岗位 JD**，一并读取：它决定要点排序、技术关键词取舍和包装方向。
- 用一句话写下项目真实核心方向（如「面向 C 端交易场景的 Java 后端服务，我主要做订单链路」），后续每条补写都回这句对齐。
- 素材极薄时（只有一两句话）也照常产出：以事实为骨架、用包装把肉补上，但把全部包装条目集中列进第八板块请用户确认。

### 第 2 步：按八个维度萃取事实

边读边记录「事实卡片」：信息本身 + 原文出处（文件名/段落线索）。

| 维度 | 必须抓到的信息 | 常见信号位置 |
|------|----------------|--------------|
| 0. 元信息 | 项目名称、起止时间、担任角色、团队规模、所属公司/业务线 | 标题、署名、文档抬头、周报表头 |
| 1. 项目背景 | 行业/业务域、要解决的痛点、项目目标、服务对象、业务价值 | 「背景」「目标」「为了解决」 |
| 2. 职责分工 | 个人职责边界、独立负责/参与/协助、协作方、汇报对象 | 「我负责」「牵头」「配合」「对接」 |
| 3. 核心任务 | 工作模块拆解、关键里程碑、交付物、推进的机制/流程 | 排期、迭代记录、目录结构、任务清单 |
| 4. 技术栈 | 语言、框架、中间件、存储、工具链、部署基建；按使用深度分级 | 技术方案、依赖清单、架构图、配置文件 |
| 5. 问题与解法 | 难点/故障/瓶颈 → 分析思路 → 落地方案 → 备选方案与权衡 | 「问题」「优化」「排查」「选型」「对比」 |
| 6. 量化成果 | 前后对比、绝对值与百分比、规模量（QPS/数据量/用户数）、时间与成本节约 | 「提升」「降低」「节省」「达到」「覆盖」 |
| 7. 经验沉淀 | 方法论、规范建设、可迁移能力、踩坑结论、对外分享/专利 | 「总结」「反思」「沉淀」「规范」 |

抓取要求：

- **技术栈深度分级**：核心使用（方案设计/核心开发）、熟练使用（常规开发）、接触了解（仅配合），三档不可混为一谈。
- **边角亮点不要漏**：故障复盘、压测数据、同事/上级表扬、专利与分享、带新人——散落在非显眼段落，却是高价值简历素材。
- **多份素材冲突时**：同一事实说法不一致，并列呈现并标注「素材间存在出入」，不替用户裁决。
- **顺手记录「说了但没写全」的线索**：原文一句「加了缓存」往往对应一整套主流做法（缓存粒度、过期策略、击穿/穿透保护），这类线索是第 4 步术语显性化的原料。

### 第 3 步：找缺口

把八维清单和该项目的「领域标配链路」对照，列出空白：没写部署方式、没写监控告警、没写数据量级、没有效果指标、职责只有参与没有主导。缺口不必都留着追问——按第 4 步判断哪些能补、哪些该问。

### 第 4 步：可控包装（三种手法，风险递增）

详细规则、红线清单、自洽检查与主流技术对照见 [references/core-packaging-rules.md](references/core-packaging-rules.md)，动手补写前必读。

| 手法 | 做法 | 风险 |
|------|------|------|
| 术语显性化 | 原文确实做了、只是没写规范叫法，按行业术语说清楚：「加了缓存」→「引入 Redis 缓存热点商品数据，设置 TTL 与空值兜底防穿透」 | 低，优先用 |
| 主流技术补强 | 该方向必然涉及、素材却没记录的工程环节，按领域默认链路补上（后端服务补 Docker + CI + 日志监控；检索功能补 ES/向量召回两阶段） | 中，须能解释原理 |
| 量级合理化 | 把「近一倍」写成「约 45%」、按行业常见区间给保守规模量（QPS、数据量、接入方数） | 中高，须用户确认 |

补写后逐条自检：① 挂在原文同一模块上，不凭空长出新职责 ② 与已有技术不互斥、时代不穿越、规模与技术不匹配的情况没有 ③ 答得出三层追问。任一不过就删。

### 第 5 步：简历化改写

- **句式公式**：动作动词 + 任务/对象 + 方法或技术手段 + 量化结果。四要素尽量齐全。
- **一条一贡献**：每条只讲一个贡献点，30~50 字（约 1~2 行），不写流水账。
- **动词开头、省略主语**；禁止以「负责了……」开头——它只表达态度，不表达产出。
- **贡献程度用五档**：主导 / 独立完成 / 推动 / 参与 / 协助。原文分不清本人作用的团队成果，写「参与」；确有个人动作支撑的，可选更强的动词。
- **技术名词保留原文写法**，不擅自把 MySQL 升级成「精通数据库优化」；但包装档位里补的技术要用行业标准名（写 Elasticsearch 而非「搜索引擎」）。
- 选词（动作动词）、量化六维、STAR 结构与反模式见 [references/core-resume-standards.md](references/core-resume-standards.md)。
- 若存在目标 JD：要点排序与详略向 JD 关键词靠拢，并在报告末尾说明「按某岗位 JD 做了排序与技术关键词适配」；红线类事实不动。

### 第 6 步：输出前回扫（强制执行）

- [ ] 八个维度每一维都有结论；原文确实没有且不适合补的，写「原文未提及」
- [ ] 每条内容带档位标记（事实 / 推断 / 包装），无标记的默认必须是事实
- [ ] 每条包装内容能挂回原文某个模块或方向，且未触碰红线清单
- [ ] 技术栈自洽：搭配合理、无时代穿越、无规模与技术不匹配
- [ ] 每条包装内容都配了面试追问与答题要点（第八板块）
- [ ] 数字前后一致，同一指标不在两处给出不同值
- [ ] 每条要点的贡献程度与原文/包装档位相符，未把「接触」写成「精通」
- [ ] 无法补、必须用户提供的信息已集中成「补充建议」里的 3~5 个具体问题

### 第 7 步：按固定模板输出

## 三、多项目与多文件处理

- **多份素材属于同一项目**：合并为一份报告，去重后在抬头列明全部来源文件。
- **素材覆盖多个不同项目**：每个项目独立产出一份完整报告；可在最前面追加一段「跨项目总览」（项目名 + 角色 + 一句话定位 + 最强亮点），帮助用户决定主推哪个项目。
- **素材为代码仓库本身**（用户只给了项目目录）：读 README、docs、提交历史与代码结构提炼技术栈与任务；提交作者的分布是判断个人职责的强信号。没有代码证据的角色与成果走包装档位并列入第八板块。

## 终检：去 AI 味（流程的最后一步）

这不是可跳过的附录。定稿前先跑扫描，再逐条过人工清单，两条都过才算交付。

`humanizer-zh` 在仓库里位于 `external/`，安装到编辑器后与其他技能平铺在同一 `skills/` 下，相对路径随布局变化。先定位脚本再跑，两种布局都覆盖：

```bash
SCAN=$(ls ../humanizer-zh/scripts/scan-ai-tone.mjs ../../external/humanizer-zh/scripts/scan-ai-tone.mjs 2>/dev/null | head -1)

node "$SCAN" 稿件.md   # 稿件已落盘
node "$SCAN" -         # 从标准输入读
```

扫描只负责把候选捞出来，判定标准在 `humanizer-zh/SKILL.md` 的 A–F 检查点（仓库内为 `external/humanizer-zh/SKILL.md`）。命中不等于必须改，承载实际信息的句子照原样保留。

必须清掉的六处：

- 空泛高频词：「赋能」「闭环」「显著提升」换成具体动作或数据
- 强凑三段式：有几项写几项，不为节奏删项或凑项
- 万能破折号：每处问一句「换成逗号或句号是否更清楚」
- 句尾拔高：结论停在事实上，不追加「这标志着……」
- 套话收尾：删掉「综上所述」「未来可期」「希望对你有帮助」
- 客服腔与免责填充：「值得注意的是」「需要指出的是」

底线是保留事实、否定、条件、归因、时间与完成状态，润色不许改变原意。

## 四、边界

- 本技能产出**简历素材与包装方案**，是否使用、改到什么程度由用户决定；报告必须让用户清楚哪句是事实、哪句是补的。
- 红线类信息（公司、时间、职级、学历、独占性可查证事实）不代填，只列进第七板块问用户。
- 用户要求直接改写整份简历时可在本报告基础上继续，仍按档位标记与红线执行。
- 报告语言与素材语言一致（中文素材出中文报告）；技术专名保留原文语言。
