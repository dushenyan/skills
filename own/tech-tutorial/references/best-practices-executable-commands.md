# 教程可执行性：环境基线与命令校验

读者照做的第一条命令跑不通，后面讲得再好也没用。这份清单解决两件事：

1. 动笔前先给整份教程定一个**环境基线**，后续所有命令都以它为参照；
2. 交付前按七个维度逐块核对。

## 一、先定环境基线

开写前用四个问题把基线定下来，写进 README 的「环境准备」和安装章开头：

| 维度 | 要定的事 | 写在哪 |
|---|---|---|
| 运行形态 | 单机 Docker、本地二进制、多机集群、K8s、云托管 | README「环境准备」 |
| 执行位置 | 命令在宿主机跑、容器内跑、还是集群节点上跑 | 每章开头一句 |
| 实例规模 | 1 个节点还是 3 个节点；副本数、分片数 | 安装章与集群章 |
| 版本与依赖 | 具体版本号，JDK / Python / Node 版本 | README「版本说明」 |

基线一旦确定，后面每一章的命令都必须与它一致。需要切换环境时，显式写「以下命令需要三节点集群」并给出搭建步骤，不要让读者猜自己现在在哪。

**为什么先说这个**：一份教程的命令跑不通，根源往往不是某个参数写错，而是不同章节隐式假设了不同环境。比如安装章是单节点容器，集群章是二进制三节点，参数章又回到单节点，读者照着做就会在「副本因子 3 只有 1 个 Broker」这类地方失败。先定基线，这类问题会在写作阶段就消失。

## 二、命令写作与自检的七个维度

以下规则与技术栈无关。案例用容器化中间件举例，换成你正在写的技术即可。

### 1. 完整性：不留占位符

可复制执行的代码块里，不要出现 `...`、`xxx`、`<your-topic>`、`TODO` 这类省略。

**反例**

```bash
docker run -d -e APP_NODE_ID=1 ... example/app:1.0
```

**正例**：参数写全；需要读者替换的，用注释点名替换位置。

```bash
# 9092 被占用时改成 9093，并同步修改对外通告地址
docker run -d --name app -p 9093:9092 example/app:1.0
```

同一段配置要在多个节点重复时（三节点集群、多副本 Compose），每条都写全，不要写「其余同上」——读者复制的是单条命令，不是上下文。

### 2. 环境一致性：命令的能力上限不能超过当前环境

单节点环境不能出现需要多节点、多副本的命令。

| 类型 | 单机环境 | 需要多节点 |
|---|---|---|
| 消息队列 | 副本数为 1 | 副本数 ≥ 2 |
| 搜索引擎 | replica 为 0 | replica ≥ 1 |
| 缓存 | 单实例 | cluster / sentinel |
| 数据库 | 单实例 | replica set / 主从 |

判断方法：命令里的每个数字（副本数、节点数、quorum 大小、分片数）都要能在这一章的基线环境里满足。

### 3. 位置一致性：同一条命令在不同执行位置地址不同

客户端命令写在宿主机、容器内、K8s Pod 里，连接地址不一样。

| 执行位置 | 该用的地址 |
|---|---|
| 宿主机，服务端口已映射 | `localhost:<映射端口>` |
| 容器内，服务在另一个容器 | 容器网络内部名，如 `<service>:<容器端口>` |
| 容器内，服务在宿主机 | `host.docker.internal`（macOS / Windows） |
| K8s 集群内 | Service 名 + 容器端口 |
| K8s 集群外 | `port-forward` 后的 `localhost:<本地端口>` |

**为什么**：很多中间件第一次连 bootstrap 地址后，会返回「对外通告地址」（Kafka 的 `advertised.listeners`、Elasticsearch 的 `network.publish_host`、Redis Cluster 的 announce 地址）。执行位置不对，第一次能连上，后面报 `Timed out waiting for a node assignment` 之类，看起来像服务挂了。

### 4. 实例一致性：每个实例独有的配置必须逐台改

多节点模板里，总有几项是每台不同的：

- 实例标识：`node.id`、`node.name`、`server-id`
- 对外通告地址：`advertised.listeners`、`announce-ip`、`external_url`
- 专属路径：数据目录、日志目录、证书路径

注释里必须写「每台改成自己的」。三台都照抄第一台的地址，流量会全打到一台，那台挂了整个集群对外不可用。

### 5. 真实性：不写伪命令

- **不存在的入口**：确认启动脚本、jar 包、二进制名真的存在。以 Kafka 为例，它没有 `kafka.jar`，JMX agent 要通过 `KAFKA_OPTS` 注入。
- **未定义的变量**：`$APP_HOME`、`$BOOTSTRAP` 第一次使用前必须赋值。
- **示例值当参数**：`cluster-id`、`token`、`topic-id`、密码，要提示「换成上一步的输出 / 你自己的值」。
- **跨网络的地址**：容器里不要写只在宿主机 `/etc/hosts` 存在的主机名。

判断方法：把命令丢进一个干净终端，缺什么它就会报什么。

### 6. 前置条件：会失败的依赖提前交代

- **主机名**：多节点用 `node1/node2/node3`，说明要写 `/etc/hosts` 或内网 DNS。
- **端口占用**：先停旧容器，或换端口并同步改通告地址。
- **运行时**：JDK、Python、Node 的版本要求。
- **资源**：大镜像、需要 license、需要管理员权限的，命令前一句说明。

### 7. 长命令必须逐项释义

满足任一条就算长命令：

- 单行超过终端宽度需要折行，或用了续行符 `\`；
- 参数或选项超过 2 个；
- 出现多个 `-e` / `--env`、多个 `-p` / `--port`、多个 `-v` / `--volume` 这类重复选项；
- 命令嵌套两层以上（`docker exec ... sh -c "..."`、`kubectl exec ... -- bash -c "..."`）；
- 含读者必须替换的变量、路径、ID，且不止一个。

**字段说明集中写在命令之前**，一张表列出每个字段的名称、取值含义，以及「为什么是这个值」。读者先看懂参数再复制命令，而不是复制完再回头猜。

**反例**：命令贴完就结束，读者不知道 `--mode` 有哪几种、`0.75` 从哪来。

```bash
milvus-backup create --name b1 --collection demo --mode skip --ratio 0.75 --workers 8
```

**正例**

| 字段 | 含义 | 为什么取这个值 |
|---|---|---|
| `--name` | 备份任务名 | 同一次实验内唯一，便于后续恢复时定位 |
| `--collection` | 目标集合 | 与本节创建的集合名一致 |
| `--mode skip` | 冲突处理策略 | 允许重复执行，避免读者中途重跑报错 |
| `--ratio` | 采样比例 | 0.75 兼顾数据量与耗时，纯示意值 |
| `--workers` | 并发数 | 取 8，不超过常见 4 核 8 线程的上限 |

参数含义清楚了，再看命令：

```bash
milvus-backup create \
  --name b1 \
  --collection demo \
  --mode skip \
  --ratio 0.75 \
  --workers 8
```

单行短命令（≤ 2 个参数、无重复选项）不必配表，用一条行内注释说明关键参数即可。判断标准是**读者是否需要停下来查文档才能改**——需要，就在命令前面写清楚。

## 三、交付前自检

对每个可执行代码块问五个问题：

1. 复制到干净终端，缺不缺参数？
2. 当前章节的基线环境（宿主机 / 单容器 / 多节点 / K8s）能满足命令里的数字和地址吗？
3. 地址、端口、副本数、实例名，与这一章的基线一致吗？
4. 有没有依赖上一步输出、却没说明要替换的值？
5. 这条命令算长命令吗？算的话，命令**前面**有字段说明表吗、每个值都解释了「为什么」吗？

能实测的本地跑一遍（Docker、CLI、kubectl），不能实测的（付费云服务、生产专属工具）在命令旁标注前置条件与预期输出。

## 要点

- 先定环境基线，再写命令；切换环境要显式声明
- 命令块是教程的可执行契约，占位符等于违约
- 数字看环境、地址看位置、配置看实例
- 长命令必然在命令前配字段说明表：每个字段讲清含义与取值理由，读者能改而不只是能抄
- 先跑脚本扫占位符，再人工过一遍上面五个问题
