# description 打磨标准

description 是技能唯一的触发入口，它的质量直接决定技能被加载的概率。打磨目标是三个词：**通用、立体、适中**——这三者有优先级：先立体（要素齐全），再通用（用词得当），最后适中（字数收敛）。顺序不能反。

## 三要素结构

一条合格的 description 按顺序覆盖三层：

1. **能力层**（做什么）：一个动词短语概括核心产出。用类别词——「生成技术教程」而不是「生成 Milvus 教程」；「审查简历」而不是「审查后端工程师简历」。能力绑死实例会缩小适用面。
2. **触发层**（何时用）：2~4 个用户会真的说出口的话或场景。这一层恰恰要具体——「生成一份 Milvus 教程」「这段中文排版检查一下」都是好触发词，因为代理做的是字面匹配加语义联想，具体原话比抽象概括命中率高。触发词不足 2 个或全是「需要时使用」这类空话，视为触发层缺失。
3. **边界层**（不用什么）：反触发（什么情况不要调用）或与兄弟技能的分工（「X 交给 skill-a，本技能只做 Y」）。有功能相近的相邻技能时，分工必写，否则两个技能抢同一个触发。分工句写成用户视角的分流规则：「要 A 找 skill-a，要 B 用本技能」，而不是抽象的能力划分。

## 风格锚点保护（阮一峰规则）

以阮一峰风格为代表的人物/风格锚点信息——人名、风格名、代表作、风格特征词（短句白话、生活化类比、先场景后概念）——在打磨时是**保护 + 突出对象**，原因有二：

1. 人名是最强触发词。用户会直接说「用阮一峰风格写」「写得像阮一峰一点」，这些原话里的锚点词一旦在瘦身时被删，技能就漏触发。
2. 风格特征描述不是「手法细节」。瘦身时「每个知识点按六要素讲透」这类操作细节该移进正文，但「生活化类比、口语化短句」这类风格特征是技能的核心资产，留在 description 里也不算超重。

操作上：改写前先扫一遍原文，把锚点词列进保留名单；改写后核对名单一个不少。仓库内适用这条的技能：`ruanyf-answer-style`、`ruanyf-document-style-guide`、`ruanyf-paper-explainer`，以及 `tech-tutorial`（叙事语气属阮一峰系）——这几个技能里的「阮一峰」三个字和风格特征词永不删除，且同系技能对风格的表述要对齐。

## 字数拿捏（300~700 字符）

| 状态 | 信号 | 修法方向 |
|------|------|---------|
| 太薄（<300） | 只有能力层；触发层缺失或空泛；无边界层 | 补触发层和边界层，见 [feature-repair](feature-repair.md) |
| 适中（300~700） | 三层齐全，读一遍能答出「做什么、何时用、不用什么」 | 不动 |
| 太厚（>700） | 出现操作手法细节（如「每个知识点按六要素讲透」）；触发示例超过 3 个；默认手法与覆盖规则挤在一句里 | 手法细节移到正文，description 只留概括 |

**要素优先于字数**：修剪超厚描述时，先保三层齐全再往区间收。宁可停在 750 字符，也不要把边界层砍掉来凑数——一条 300 字符但没边界的描述，比 750 字符三层齐全的更容易造成误触发。

## 通用性与立体度

- **立体** = 三层信息各就各位。扁平的反面样本：只有能力层 + 一句「在设置项目时使用」。
- **通用** = 能力层用类别词、触发层用实例词。这两个方向的「具体」不矛盾：能力越宽越好，触发越像用户原话越好。
- **通用还延伸到正文示例**：技能正文和 references 里的具体示例（类比清单、正反例、指标组合、示例对话中的材料）要么配构造方法（「三步现做一个」），要么标注「仅演示结构/流程」。绑死单一领域又无说明的示例是素材库——用户解读一篇数据库论文时，模型会照抄 QKV 类比或被它带偏。语法演示（公式排版、引用格式）不受此限，内容无关紧要。
- **克制** = 每层内部不展开。判断标准：这句话删掉后，代理决定「是否加载」时会变难吗？不会就删——它属于正文。

## 使用

改写前先读该技能的正文，从正文里提炼触发层和边界层的素材，而不是凭空编——description 说的必须是技能真能兑现的。

改写后自检三问：只读 description，我能说出它做什么吗？遇到什么话该想起它吗？什么情况下它不该出场吗？三问都过，字数落在区间内，才算完成。
