# Article Readability Rewriter

文章不好读，九成不是内容少，而是**顺序、形态、密度**出了问题。

同样的材料，换个讲法，读者就愿意看完。这个技能管的只是讲法，不改事实。

定稿前必须走「终检：去 AI 味」，见本文同名章节。

## 动笔前先判断三件事

跳过这三问直接改，很容易把一篇好文章改成另一种平庸。

**1. 这篇靠什么吸引人？**

| 吸引力来源 | 读者的心思 | 主要靠什么 |
|---|---|---|
| 认知型 | 我想弄懂 | 清晰、画面、实例 |
| 情绪型 | 我想被说中 | 冲突、故事、具体的人 |
| 决策型 | 我要判断值不值 | 结论、证据、对比 |

判断错了，杠杆就用反。给决策型文章堆故事，读者会嫌慢；给情绪型文章堆论证，读者会觉得冷。

**2. 读者是谁，在哪读？**

手机上看公众号，和在工作群里看文档，容忍度完全不同。前者要短句、要钩子；后者要结论、要能跳读。

**3. 用户要改到什么程度？**

- 只改开头：给三个开场方案
- 改结构：给新骨架，标出迁移了哪些段落
- 改全文：给完整新稿
- 只润色：保留骨架，逐段替换措辞

不确定时按「改全文」处理，但先给三条诊断让用户确认方向。

## 三条通用病根

不同文体的坏文章，病因高度一致：

1. **陌生概念先于场景。** 读者还不知道这东西干什么用，就先读到它的定义。
2. **过程晚于来历。** 要熬过背景、历史、意义，才看到它到底怎么运作。
3. **结论重复多遍。** 同一个判断说四次，读者会以为你后面没新东西。

诊断就找这三样，找到哪条，对应下面的杠杆。

## 十个杠杆

按收益排序，分属四类：顺序（1、2、7）、形态（3、4、6）、密度（5、10）、语气（8、9）。时间紧就做前四条。

### 1. 先看见，再听见

陌生名词出现之前，先让读者看到一个动作、一个画面。

- ✘ 先说「本系统采用异步消息队列解耦」。
- ✔ 先说：下单那一刻，用户已经收到短信，库存却还在慢慢扣。中间隔着的，就是那个队列。

规则：**每个新名词首次出现的前一段，必须有一个能想象的动作或后果。**

### 2. 先演一遍，再讲来历

最劝退的结构是：问题 → 背景 → 定义 → 流程。读者要熬过三节才看到全貌。

改成：问题 → **完整过程演一遍** → 没有它的年代 → 概念 → 深化。

有了画面再听「当年多痛」，才有共鸣。背景从铺垫变成回顾，读者反而看得下去。

### 3. 抽象配类比

每个抽象概念配一个类比，紧跟解释之后。三原则：

- **贴**：读者天天见的场景，点菜、问诊、搬家、查字典
- **准**：机制真的对得上，不为形象牺牲准确
- **短**：一两句讲完，不展开成长篇比喻

格式：`**打个比方**：……`

凑不出合适的类比，就老实解释一遍。硬凑的类比比没有更糟。

### 4. 抽象落地成实证

每个抽象说法，配一个能对照、能验证的东西：代码、截图、对话记录、数据表、原始日志、真实案例。

一句「效果显著」不如一张前后对比图。一句「流程复杂」不如一段三方的聊天记录。

要求：实证必须**真实存在、能对照**。伪代码和编造的案例，比没有更伤信任。

没有实证就留空，写「这里待补一组数据」。

### 5. 重复只讲一次

核心结论全文讲一次，位置选在第一次需要它的地方。后面用类比、代词或实例带过。

删句子的唯一标准：**这句话删了，读者会缺什么？** 缺不了就删。

同义反复最伤信任。读者会以为你在凑字数。

### 6. 反直觉点独立成节

每篇好文章都有一个「你以为 A，其实 B」。它往往是全文信息量最大的地方。

常见错误：把它塞进「注意事项」列表的第六项，读者扫一眼就过去了。

做法：单独一节，开头一句直接打脸，再解释为什么。

### 7. 结论前置

把最凝练的一句放到开头，当全文地图。

读者带着框架往下读，注意力更稳；读到结尾还有「果然如此」的闭合感。

注意：前置的是**结论**，不是**摘要**。摘要是目录，结论是判断。

### 8. 作者在场

每篇加一到两处「我」：踩过的坑、当时的困惑、后来怎么想明白的。

点到为止，禁止鸡汤和煽情。

作用是拉近距离：读者会觉得这是人在讲，不是文档在播报。

### 9. 节奏起伏

长度均匀是坏文章的共同特征。每节都四行，读起来像表格。

做法：关键节写长、写细，过渡节压到两三行。列表只用于真正的并列项，不要通篇清单。

### 10. 压缩一到两成

同义反复、穿靴戴帽、客套、重复铺垫，全砍。

压缩后信息密度上升，兴趣自然上升。这是最不需要技巧、收益却最确定的一条。

## 常见文体怎么改

先按上面的「吸引力来源」定方向，再对照这张表挑杠杆。表里没有的文体，用三条病根自己判断。

| 文体 | 主攻杠杆 | 抓手 |
|---|---|---|
| 概念讲解 | 1、3、4 | 场景开场，概念配类比，说法配实证 |
| 操作教程 | 2、4 | 先跑通最小例子，再讲参数与原理 |
| 观点评论 | 6、7 | 开门见山抛判断或冲突，再逐层论证 |
| 产品介绍 | 1、7 | 先写用户此刻的窘境，再给功能 |
| 论文解读 | 2、6 | 旧方法的局限讲透，新方法的直觉先给 |
| 项目复盘 | 7、9 | 数字和结论前置，过程作为证据 |
| 经验分享 | 8、1 | 从一次具体经历起手，再提炼方法 |

## 改写流程

1. **通读并标注。** 标出你自己读到第几段开始走神。那就是要动刀的地方。
2. **写三条诊断。** 顺序、形态、密度，各一句。
3. **重排骨架。** 先演后讲，结论前置。
4. **逐节补料。** 类比、实证、作者视角，缺哪个补哪个。
5. **删重复与铺垫。** 目标是减一到两成。
6. **校对。** 中文排版面向技术或商务文档时，查中英空格、全角标点、超长句。文学、演讲类稿件按各自习惯来，不套这条。
7. **交付。** 先给诊断，再给改写，最后给改动理由。

## 终检：去 AI 味（流程的最后一步）

这不是可跳过的附录。定稿前先跑扫描，再逐条过人工清单，两条都过才算交付。

`humanizer-zh` 在仓库里位于 `external/`，安装到编辑器后与其他技能平铺在同一 `skills/` 下，相对路径随布局变化。先定位脚本再跑，两种布局都覆盖：

```bash
SCAN=$(ls ../humanizer-zh/scripts/scan-ai-tone.mjs ../../external/humanizer-zh/scripts/scan-ai-tone.mjs 2>/dev/null | head -1)

node "$SCAN" 稿件.md   # 稿件已落盘
node "$SCAN" -         # 从标准输入读
```

扫描只负责把候选捞出来，判定标准在 `humanizer-zh/SKILL.md` 的 A–F 检查点（仓库内为 `external/humanizer-zh/SKILL.md`）。命中不等于必须改，承载实际信息的句子照原样保留。

必须清掉的六处：

- 空泛高频词：「赋能」「闭环」「显著提升」换成具体动作或数据
- 强凑三段式：有几项写几项，不为节奏删项或凑项
- 万能破折号：每处问一句「换成逗号或句号是否更清楚」
- 句尾拔高：结论停在事实上，不追加「这标志着……」
- 套话收尾：删掉「综上所述」「未来可期」「希望对你有帮助」
- 客服腔与免责填充：「值得注意的是」「需要指出的是」

底线是保留事实、否定、条件、归因、时间与完成状态，润色不许改变原意。

## 输出约定

- 默认先给三条诊断，再给改写。用户说「直接改」就跳过诊断。
- 改动理由只讲**为什么**：读者会缺什么、会卡在哪、会误读什么。
- 全文改写保留原稿每个要点，不悄悄删内容。要删就说明删了什么。
- 段落级对照用「原文 → 改写」，让用户一眼看到差别。
- 一次给太多方案会挑花眼。方向未定时最多给三个开场或三种骨架。

## 边界

- 不编造事实、数据、案例。没有就留空或标「待补」。
- 类比必须机制对得上，凑不出就明说。
- 保留原作者的语气与立场，不要把每篇都改成同一种腔调。
- 规范文档、合同、API 参考不该做结构改写，只做纠错与一致性检查。
- 用户只要校对或排版时，不动结构。
