# Makefile 组织规范

Makefile 是项目操作的唯一入口。写的人按分类放命令，用的人只读 `make help`。本技能只约束四件事：**分类**、**总命令**、**终端反馈**、**排版**——不绑定语言、包管理器或部署方式，Python、Go、Node、Rust 项目同样适用。

## 四条硬规则

| 规则 | 要求 | 反例 |
|------|------|------|
| 分类 | 用编号章节注释 `# 1. 依赖` 分段，章节顺序固定；按**操作对象**分章，不按执行阶段硬合并 | 命令按添加时间堆在一起；把打包发布和容器操作都塞进「部署」，只因它们都在上线阶段 |
| 总命令 | 每个分类必须有一个聚合入口，子命令只做单件事 | 只有 `build-lib` / `build-app`，没有 `build` |
| 反馈 | 每个多步骤命令在开始、阶段切换、结束时给出重点提示 | 跑完只看到一堆无意义的命令回显 |
| 排版 | 章节间空行 + 分隔线，help 从行尾 `##` 自动生成 | 手写 help，命令一改就过期 |

## 应用流程

1. **盘点命令**：先按操作对象分组（发布打包、容器操作、数据运维…），再按「依赖 → 开发 → 构建 → 质量 → 部署 → 清理 → 运维」排序。同一前缀的命令（`docker-*`、`db-*`）自成章节——它们操作的是同一个对象，混进「部署」会让 help 分不清哪些是上线动作、哪些是日常运维。归不进去的说明它是子命令，应当挂到某个总命令下。
2. **先定总命令**：每个分类先写聚合 target（如 `build`、`check`、`serve`），再写它依赖的子命令。总命令是默认路径，子命令是 CI 与局部调试用的零件。
3. **套用模板**：结构、变量区、help 的 awk 实现见 [Makefile 模板](references/makefile-template.md)，直接复制后删掉不用的分类。
4. **自检**：跑一遍 `make help`，逐条对照源文件——确认每个 target 都出现在目录里（漏写行尾 `##` 的会消失）、分组正确、分类名不带序号、列对齐、别名没有重复出现；再确认每个分类的总命令能独立跑通。

## 分类参考

分类数量和名称随项目定，只要求：**顺序稳定、序号连续、一个分类只放同类命令**。下表是常见起点，用不上的整段删掉，缺的按同样格式补：

| 序号 | 分类 | 典型总命令 | 子命令 |
|------|------|------------|--------|
| 1 | 依赖 | `install` | `update-deps`、`uninstall` |
| 2 | 本地开发 | `dev` / `serve` | `serve` 依赖 `build` 后再启动 |
| 3 | 构建 | `build` | `build-lib`、`build-app` |
| 4 | 质量检查 | `check` | `lint`、`typecheck`、`test` |
| 5 | 部署 | `deploy` | 打包、发布、托管等一次性上线动作 |
| 6 | 容器 | `docker-build` | `docker-up`、`docker-down`、`docker-logs` |
| 7 | 清理 | `clean-all` | `clean` |
| 8 | 运维（可选） | `init` | `path`、`migrate`、`status`、`restart` |
| 9 | 帮助 | `help` | — |

同前缀命令组不需要再造 `docker: docker-build` 这类纯转发别名——它只是把既有命令换个名字重复一遍。组内应有一个语义完整的命令（如 `docker-build`）作为默认路径，在行尾 `##` 里标注「默认入口」即可；只有组内全是片段命令、没有任何一个走完整流程时，才需要补一个真正做编排的总命令。

编号只用于源文件里的排序与定位，`make help` 输出时不带编号，只显示分类名。

「依赖」在 Python 项目里是 `uv sync`，Go 是 `go mod download`，Node 是包管理器 `install`；分类含义不变，命令随技术栈替换。

## 总命令的写法

总命令只做编排，不写实现细节；子命令各自可独立执行。下例中的构建命令按项目替换：

```makefile
# 构建全部（库 + 应用）
build: build-lib build-app

# 构建库
build-lib:
	npm run build:lib

# 构建应用
build-app:
	npm run build:app
```

「构建后启动」用依赖表达，不要复制粘贴命令：

```makefile
# 构建后启动独立服务
serve: build
	node apps/server/index.mjs
```

## 终端反馈

多步骤命令（拉代码、构建镜像、迁移数据）不能只留一串命令回显。每个阶段要有「开始做什么 → 结果 → 下一步」三段提示，关键值缩进对齐：

```makefile
# 拉取最新代码并构建部署镜像
docker-build:
	@echo ""
	@echo "  ⬇️  [1/2] 拉取最新代码"
	git pull
	@echo "  ✅ 代码已更新"
	@echo ""
	@echo "  🐳 [2/2] 构建镜像 $(APP_IMG):$(APP_TAG)"
	docker build -t $(APP_IMG):$(APP_TAG) .
	@echo ""
	@echo "  ✅ 镜像构建完成: $(APP_IMG):$(APP_TAG)"
	@echo "     下一步: make docker-up"
	@echo ""
```

| 位置 | 写什么 |
|------|--------|
| 开始 | 阶段编号 `[1/2]` + 正在执行的动作，让等待有预期 |
| 阶段之间 | 上一阶段的结果 `✅ 代码已更新`，再接下一阶段 |
| 结束 | 结果 + 关键值（镜像名、端口、路径）+ 下一步命令 |
| 失败 | 不手写：命令非零退出即中止，make 自带错误输出 |

规则：

- 提示行前加 `@` 抑制命令回显，只留提示本身；不加 `@` 会把 `echo "..."` 原文也打出来。
- 整段提示前后各留一个空 `@echo ""`，终端输出才有呼吸感。
- 关键值第二行缩进 5 个空格对齐，例如 `访问    : http://localhost:$(PORT)`。
- 一个阶段一行提示，不要把多条信息挤进一句。
- 阶段编号必须全局一致：步骤增删后同步所有编号。原本 `[1/3]`、`[2/3]`、`[3/3]` 后面追加第 4 步，前三步要一起改成 `[1/4]`、`[2/4]`、`[3/4]`，否则「还要等几步」的信息是错的。
- 是否需要阶段提示看**步骤数**，不看命令名：`clean` 一眼可见结果时不必加；若它同时杀端口、删目录、清缓存，就是多步命令，照样要编号。
- 前台常驻命令（`dev`、`serve`、`deploy`）的结束提示必须写「前台运行，Ctrl+C 退出」：否则使用者分不清服务是启动成功还是命令卡住了。

## 成对命名与精简

同一动作组的命令必须成对、对称，实现保持最短——能用一个参数表达方向，就不写两段逻辑：

| 动作组 | 正向 | 反向 | 精简实现 |
|--------|------|------|----------|
| 服务 | `up` | `down` | `$(COMPOSE) up -d --build` / `$(COMPOSE) down` |
| 依赖 | `install` | `uninstall` | 各自一行包管理器命令 |
| 构建 | `build` | `clean` | 各一行构建 / 删除命令 |
| 本地 | `dev` | — | 前台运行，`Ctrl+C` 即停，不必造反向命令 |

- 命名用同一动词词根：`up` / `down`、`init` / `clean`、`build` / `clean`。
- 子命令只写一行实际命令，提示与编排留在 target 内，不抽脚本、不加中间变量。
- 成对命令的输出也要成对：`up` 给访问地址，`down` 给「如何重新启动」。
- 兼容别名（如 `docker-prod: docker-build`）不写行尾 `##`：help 里只该出现主命令，别名保留可用即可，避免目录里出现两个语义相同的条目。

## 排版要点

| 位置 | 约定 |
|------|------|
| 文件头 | 项目名 + 用法 + `make help` 提示，用 `# ====` 包住 |
| 变量区 | 按「可调参数 → 派生变量 → export」三段；可调参数一律 `?=`，允许命令行覆盖 |
| 章节 | `# ====` 分隔线 + `# N. 分类名`，章节之间空一行 |
| 注解 | 行尾 `## 一句话` 供 help 提取（**必须与 target 同一行**）；解释「为什么」的说明写在 target 上方，不会进 help |
| 收尾 | 多行 `@echo` 前后各留一个空 `@echo ""`，让终端输出有呼吸感 |
| help 层级 | 标题粗体 + 暗色分隔线；分类名粗体不带颜色；命令名加粗亮色（`\033[1;32m`）；描述用默认色；分类之间空行；末尾不追加用法/覆盖变量之类的广告行 |

## 常见坑

- 行尾注释与变量赋值写在同一行时，注释前的空格会混进变量值；参数说明单独成行。
- `export FOO` 的变量名必须与定义完全一致，写错名字不会报错，子进程只会拿到空值。
- recipe 行必须是 Tab；编辑器把 Tab 转成空格后报 `missing separator`。
- `make help` 只认 **与 target 同一行** 的行尾 `##`；写在 target 上方的 `##` / `#` 注释块只是普通说明，不会被提取进目录。长说明可以放上方，但 target 行尾必须另外补一句简短 `##`，否则该命令在 help 里直接消失（重构时最容易批量踩这个坑）。
- 行尾 `##` 的描述里 **不要写 `$(VAR)`**——awk 读取的是 Makefile 原文，不会展开 make 变量，help 会原样显示 `$(PORT)` 这类字面量。需要展示变量值就放在运行时 recipe 的 `@echo` 里，help 描述只写静态文本。
- help 的 awk 匹配 target 用 `[a-zA-Z0-9_-]+`（含数字）；写成 `[a-zA-Z_-]+` 会漏掉带数字的命令，如 `test-2`、`migrate-v3`。
- help 的 awk 用 `FS = "## "` 切分，不要用 `.*?` 非贪婪——mawk（Debian/Ubuntu 默认 awk）不支持非贪婪，描述里出现第二个 `##` 时会切错。模板里的写法已规避此问题。
- 分类最容易犯的错是按「阶段」而不是「对象」：打包发布和容器启停都在上线时用，但它们不是同一类操作，混在一章会让 help 失去导航作用。
- 别名如果也写了行尾 `##`，会作为独立命令出现在 help 里，读者会以为存在两个不同操作；兼容旧入口的别名一律不写 `##`。
