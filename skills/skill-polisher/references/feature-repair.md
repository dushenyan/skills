# 修复手法

诊断报告得到用户确认后，按问题类型选对应手法。所有改写遵循同一条底线：**只动结构与表述，不动技能的实质技术判断**——某技能的评分量表、教学步骤、默认手法本身是它的内容资产，打磨时原样保留，只调整它们「放在哪」和「怎么说」。

## 补薄描述（<300 字符）

1. 通读该技能正文与 references，列出：核心产出、典型使用场景、与其他技能的重叠区。
2. 按 [core-description](core-description.md) 的三要素顺序组织：能力层（正文第一段通常已有素材）→ 触发层（从正文的工作流里反推用户会在什么节点开口）→ 边界层（看相邻技能的 description，写清分工）。
3. 素材不足时不要编造能力——宁可写得保守，也不能让 description 兑现不了。

## 给重描述瘦身（>700 字符）

1. 划出三层归属：每句话标注它属于能力层/触发层/边界层/手法细节。
2. **先列保留名单**：阮一峰等风格锚点词、人名、用户原话式触发词、兄弟技能分工句——这些即使显得「细节」也不进删除候选（见 [core-description](core-description.md) 的阮一峰规则）。
3. 手法细节句移到 SKILL.md 正文或对应 reference，description 换成一句概括（「默认手法见正文，可被用户要求覆盖」）。
4. 触发示例砍到最多 3 个，保留最像用户原话的；锚点词触发例优先保留。
5. 瘦身后跑三问自检（见 core-description 的「使用」节），不达标回退。

## 补技能间引用

诊断出孤岛技能对（见 core-checklist 维度六）后：

1. 读两边技能的 description 与正文，找出真正的分工线——通常在输入输出形态（「素材 → 简历要点」 vs 「简历 → 诊断报告」）或流程上下游（先澄清需求再执行）。
2. 分工线写进两边的 description 边界层，各一句，互相指向：A 说「X 交给 B」，B 说「X 归 A，本技能只做 Y」。单向引用改双向。
3. 分工有实质内容（不止一句能说清）时，在 SKILL.md 开篇段后加引用块，格式参照 `inspect-resume` 的写法：`> 与 skill-x 分工：……需要 Y 时交叉引用，不在此重复。`
4. 只写真实存在的分工，不为引用而引用——两个技能若无重叠触发区，不硬造关联。

## 补结构

- 缺标题/开篇段：从 frontmatter 和正文首节提炼，不新造信息。
- 缺「核心参考」表：正文里成段的细节就地拆成 reference 文件（命名带前缀），SKILL.md 留索引行。
- 断链：优先修文件名或补建文件；确认无用的引用直接删行。
- 孤儿文件：能并入相近主题文件的就合并（保留更完整的那份内容），独立有价值的补进表格索引。

## 收尾：版本号与元数据

每改完一个技能：

1. `metadata.version` 更新为当日日期（`YYYY.M.D`）。
2. `GENERATION.md` 若无来源与时间字段则补齐；手动维护的技能写 `手动创建`。
3. 新增或删除了技能目录时，同步 README.md 清单（见 [feature-sync](feature-sync.md)）。
4. 全部修完后用诊断清单**复扫一遍**，确认报告里圈定的问题清零——复扫用同一张总表对照，新增问题如实上报，不悄悄扩大修复范围。
