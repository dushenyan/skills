# 通用中文技术教程生成器

按用户给出的技术名、主题或素材，生成一份**结构完整、内容充实、重点突出**的技术教程。默认手法是：排版对齐 [菜鸟教程](https://www.runoob.com)，叙事语气贴近阮一峰（[ruanyifeng.com](https://www.ruanyifeng.com)），核心章节配一个可运行的项目案例，重点示例抽成脚本落到示例库 `~/Desktop/engineering_examples`。目标是让读者**一章读透一个知识点**，而不是走马观花。

**默认手法整体可被覆盖。** 用户如果点明了语言、篇幅、读者、范围、语气、输出形态或落位路径，以用户要求为准——不要拿默认手法去顶撞用户。Step 0 专门处理这件事。

**一次性交付整份教程**：不要逐章征求确认，也不要写完后逐章回读返工。**章数由知识点决定，不硬凑也不刻意压缩**；常见、高频、易错的知识点必须给足篇幅展开。

## 一、基础指标 + 可调节旋钮

下面是教程的默认基线。**Step 0 解析完用户意图后，这些旋钮要跟着拨动**——用户要短就收、要深就放、要专项就聚焦。调整原则：拨一个旋钮时，观察其他旋钮有没有连锁影响，保持整体协调。

旋钮里写的范围只描述「默认能怎么收」，不是用户可选项的边界。用户如果在旋钮之外提了明确要求（要英文、要单文件、要落在指定项目目录、要用公司模板），直接照办，不必强行套回表格。

| 旋钮 | 默认值（完整版） | 调节范围 | 调向信号 |
|---|---|---|---|
| **内容深度** | 每个知识点按「是什么/为什么/怎么用/场景/坑/小结」六要素讲透，常见项给 2~3 个变体 | 精简：六要素缩成「是什么/怎么用/小结」三要素、每知识点 1 个示例；完整版不动 | 用户说"短一点"、"快速上手指南" → 精简；"讲透"、"深入" → 完整版 |
| **重点突出** | 每章至少 1 处 `> 学习重点 ⭐` + 1 处 `> 注意`；易错点单独成块 | 精简：只在核心概念章标注；完整版不动 | 用户没提 → 默认每章都给；用户说"只看核心" → 只在核心章标注 |
| **覆盖面** | 排目录前列知识点清单（官方目录 + 常见用途），逐项查漏；必备骨架 + 按需章节 | 精简：砍掉选型对比、进阶应用、FAQ，只保留必备骨架；专项：只讲用户指定方向 | 用户说"入门"、"快速" → 砍按需项；"专项讲 XX" → 只保留 XX 相关章 |
| **实战项目** | 端到端六小节项目，中文资源优先、链接验证 | 精简：只有 Hello World，不配完整项目；完整版不动 | 用户说"短一点" → 砍实战项目，快速开始章多写几个变体顶上 |
| **配套示例脚本** | 2~5 个脚本落 `~/Desktop/engineering_examples/<主题>/` | 精简：0 个（正文代码就是给"跑"的，读者直接复制执行）；完整版不动 | 用户没提 → 默认生成；用户说"教程就行，不用脚本" → 跳过 Step 4 |
| **语气** | 阮一峰手感：问题驱动、口语短句、偶尔类比 | 不变——语气是风格底线，不随篇幅调节 | — |
| **结构** | 三级目录 + 编号连续 + 章末下一站建议 | 不变——目录结构和导航是读者体验的底线 | — |
| **代码/命令可执行** | 环境基线 + 命令六维校验 + Python 用 uv + Google docstring | 不变——可执行性是教程的契约底线 | — |
| **排版** | 中文全角标点、代码块标语言、单篇 ≤ 2 处分割线、每 2~3 章一处配图建议 | 配图建议可随篇幅精简（精简版每 4~5 章一处），其余不动 | 用户说"短一点" → 配图建议密度降一档 |

所有调节都是**向下压缩**，没有"向上膨胀"的旋钮——默认完整版已经是上限。

细节都在 `references/`，按需查，不要一开始就全读。

## 二、工作流（六步）

### Step 0 · 用户意图解析与规则适配

**第一步永远是：先把用户这次到底要什么搞清楚，再拨动旋钮。** 不要一上来就搜版本号、排目录——那是默认完整版的做法。

#### 0.1 提取意图清单

把用户说的话拆成几条独立的意图项，每条对应一个旋钮：

| 意图类型 | 用户可能的表达 | 对应旋钮 |
|---|---|---|
| **篇幅** | "短一点"、"快速上手"、"精简版"、"入门就好" | 内容深度 → 精简；覆盖面 → 砍按需项；实战项目 → 砍；配套示例脚本 → 0 |
| **深度** | "讲透"、"深入"、"进阶"、"不要太浅" | 内容深度 → 完整版不动 |
| **范围** | "专项讲 XX"、"只讲核心 API"、"只要部署部分" | 覆盖面 → 只保留 XX 相关章；其余按需章节全砍 |
| **读者画像** | "纯小白"、"适合 0 基础"、"给后端开发看"、"给运维用" | 覆盖面（选型对比是否保留、前置知识章节是否详细）；语气（类比密度）；代码（示例是否配完整注释） |
| **配套** | "教程就行，不用脚本"、"代码尽量多" | 配套示例脚本 → 0 或保留 |
| **语言/风格** | "全英文"、"用更通俗的话"、"像阮一峰那样"、"不要那套语气" | 语气；代码注释语言 |
| **输入形态** | 只给技术名 / 给了一份文档、仓库或 URL / 已有教程要改造 | 只给技术名 → 走 Step 1 搜索；给了素材 → 先读素材再定目录，搜索只补缺口；已有教程 → 以原结构为基线做增量，不推倒重来 |
| **技术类型** | 库或 SDK、框架、中间件、云服务、编程语言、工具链、算法或方法论 | 决定章节骨架：中间件要部署与运维章，云服务要控制台操作 + 配额计费，语言要语法 + 标准库 + 生态工具，算法要原理 + 复杂度 + 实现对比 |
| **交付形态与落位** | "只要一个 md"、"要 HTML"、"放在我们仓库的 docs/ 下"、"要能直接发布" | 默认三级目录 Markdown；指定路径就写到那里，指定格式就换输出形态，`_meta.yaml` 等默认产物跟着调整或跳过 |
| **既有项目约束** | "放在我们仓库里"、"按现有 docs 结构"、"我们有 AGENTS.md 规范" | 先读该项目的 README / AGENTS.md / 既有 docs，沿用其目录、命名、front-matter 与构建方式，默认手法让位 |
| **显式指定** | "20 章左右"、"至少 5 个实战案例"、"每章 1000 字以内"、"基于 1.2 版本写" | 手动覆盖默认值 |

用户没说的，用**默认完整版**。用户说了但不在表里的，同样记进方案，标注「覆盖默认手法：XXX」。

#### 0.2 生成调节方案

把意图清单映射到第一节的旋钮表，产出一份**本次教程的调节方案**——在脑子里过一遍就行，不用写文件：

> 例：用户说"给我一份 Milvus 快速上手指南，别太长，纯小白能看懂"
> → 内容深度：精简版（三要素 + 每知识点 1 个示例）
> → 覆盖面：砍选型对比、进阶应用、FAQ，只留必备骨架 + 基础操作
> → 实战项目：砍，Hello World 章多给 3 个变体
> → 配套示例脚本：0
> → 语气：类比密度拉满，每章至少 1 个生活化类比
> → 重点突出：精简版，只在核心概念章标注

**这一步的目的不是让用户确认**——用户没说"帮我确认方案"就不要停下来问。而是让你自己在动笔前想清楚：哪些章节要砍、哪些要合并、哪些给足篇幅。想清楚了直接进 Step 1。

---

**Step 1 · 摸底（搜索不超过 3 次）**

- **先看手里有什么**：用户给了文档、仓库、URL、PDF、旧教程或明确版本时，先读这些素材，搜索只用来补缺口，素材里已有的信息不重复搜。
- 只给技术名时，WebSearch 一次确认最新稳定版本号与安装方式；要写实战项目，再搜一次官方 Quickstart 当素材。
- 用户指定了版本或环境就锁定，不擅自替换成最新版；版本号仍要在教程里写明。
- 不要为「版本 / 安装 / Demo」各搜一轮以上；查不到就用官方文档对应页面，并注明版本差异。

**Step 2 · 知识点清单与排目录**

读 `references/tutorial-structure.md`，先照官方文档目录和该技术的常见用途列一份**知识点清单**（每项标注「必备 / 进阶 / 可略」），再按 Step 0 的调节方案**取舍排章节目录**——调节方案说"砍选型对比"就直接砍掉，不用纠结。**逐项对照清单查漏**：完整版要覆盖全部，精简版只覆盖"必备"项；漏了要么补章要么并入相关章，确认无遗漏后**直接开写**，不要停下来等确认。

**Step 3 · 一次性写完全部章节**

- 动笔前读一次 `references/narrative-style.md` 找语感，同时对照 `references/tutorial-structure.md` 第二节的「内容深度基线」——完整版按六要素讲透，精简版按 Step 0 说的三要素讲；排版拿不准查 `references/formatting.md`；写实战章节（如果 Step 0 没砍）读 `references/project-case.md`。同一份文件整场只读一次。
- 常见/高频知识点：完整版给 2~3 个变体，精简版给 1 个；易混概念完整版用对比表，精简版用一两句话区分即可；易错点完整版单独用 `> 注意` 成块提醒，精简版只在容易炸的地儿插一句。
- 动笔前先定本教程的**环境基线**（运行形态、执行位置、实例规模、版本与依赖），写进 README 的「环境准备」与安装章开头；后续章节的命令一律对齐基线，切换环境必须在那一节显式声明并给出搭建步骤。
- 写命令时遵守 `references/best-practices-executable-commands.md`：参数写全、单机示例只给单机能力、地址随执行位置变化、每实例独有的配置逐台改、不写伪命令。
- 实战章节（如果保留）优先中文 / 国内可访问资源，资源链接必须验证可访问（通常 3~5 条）；其它章节只给官方文档链接，不必逐个访问。严禁编造 URL。
- 写完直接进 Step 4（如果 Step 0 说要跳过配套脚本就进 Step 5），**不要逐章回读、逐章重写**；动笔时顺手记下哪几个示例值得抽进示例库，省得回头翻。

**Step 4 · 重点示例抽进示例库（可跳过）**

Step 0 调节方案说跳过配套脚本时，**直接进入 Step 5**。否则从正文里挑 **2~5 个**最能帮读者建立手感的示例（通常是核心用法、对比实验、易错演示这三类），在 `~/Desktop/engineering_examples/` 下**新开一个主题目录**落成编号可运行脚本。动笔前读 `references/code-examples.md`，照仓库约定写：头部 docstring、计算值 `calc()` 下划线、关键结论高亮块、结尾要点总结；只新增目录，不改 `utils.py`/`config.py` 等既有文件。写完**逐个实际运行验证**（LLM 主题用 `USE_MOCK=1` 离线跑通），再回到教程正文，在对应小节末尾标注脚本路径。

**Step 5 · 自查一次，收尾交付**

先判断这次的产出是不是「三级目录 + 默认落位」形态：

- **是**：跑下面的脚本，把 ERROR 清零。
- **否**（单文件、用户指定目录、HTML 或其它格式、落在既有项目结构里）：跳过脚本，按本节末尾的人工核对清单过一遍。

```bash
python3 scripts/check_tutorial.py <教程目录>
```

脚本只兜底**协作必需的机械项**：文件命名与序号连续、代码块闭合（ERROR）；代码块语言标注、章末「下一站建议」、学习重点标注覆盖度、命令占位符（`...` / `xxx`）只提醒（WARN）。ERROR 改完即止；WARN 扫一眼就好——**WARN 提示某章缺少 `> 学习重点 ⭐` 或 `> 注意` 时，回到该章把常见/易错点显式补上**，这是「重点突出」的兜底。标点、字间距、句长、语气等纯写作风格脚本一律不查，写的时候顺手留意即可。

不跑脚本时，人工核对这六项：代码块都标了语言、章与章之间自然过渡、重点处有标注（用户没禁用默认手法时）、没有 `...` / `xxx` 占位、命令与环境基线一致、链接可访问。

最后再对每个 `bash` 代码块做一次命令审查（四个问题见 `references/best-practices-executable-commands.md` 的「交付前自检」）：能实测的本地跑一遍，不能实测的在命令旁标注前置条件与预期输出。

最后，默认形态下补 `README.md`（目录结构、依赖安装、项目运行方式）和根目录 `_meta.yaml`（教程目录树清单，文件节点带不重复 UUID，规范见 `tutorial-structure.md` 第五节第 4 小节）。用户指定了别的落位或格式时，按用户的形态收尾，不强塞这两个文件。

## 三、引用文件

| 文件 | 什么时候读 | 适用条件 | 内容 |
|---|---|---|---|
| `references/narrative-style.md` | 动笔前整场读一次，找语感 | 用户没有指定别的话术风格时；指定了就以用户为准 | 五条可上手的写法、类比怎么给、什么时候要展开讲、容易出戏的表达、想更严格时的去处 |

## 四、输出格式

以下是**默认形态**，用户指定了目录、文件名、输出格式或落位路径时以用户为准。

- 三级目录：技术名目录 → 学习阶段子目录 → 章节文件，命名 `<序号>-<中文标题>.md`；完整示例见 `tutorial-structure.md` 第五节。
- 正文从一级标题开始，**不要加「参考来源」引用行**，官方资源统一放最后一章。
- 教程根目录补 `README.md` 与 `_meta.yaml` 目录树清单（UUID 约定见 `tutorial-structure.md` 第五节第 4 小节）；配套示例落在 `~/Desktop/engineering_examples/<主题>/`，正文对应小节末尾标注脚本路径。
- 单文件教程：去掉三级目录与 `_meta.yaml`，其余（章节层级、章末过渡、代码规范）照常适用。

## 五、示例对话

### 示例 1：默认完整版（用户没提任何调节要求）

**用户**：帮我生成一份 Milvus 教程，菜鸟风格。

**Skill 行为**：

0. **意图解析**：用户只给了技术名 + 风格要求，没提篇幅、深度、范围 → 全部旋钮走**默认完整版**。
1. 搜一次版本与安装方式，再搜一次官方 Quickstart 作为实战素材。
2. 读 `tutorial-structure.md`，列 Milvus 知识点清单、对照查漏后排章节目录，按完整版六要素直接开写。

### 示例 3：非默认形态（项目既有约束 + 用户要求换风格）

**用户**：按我们仓库 `docs/` 的结构，给 Redis 写一份面试导向的知识点梳理。单文件 Markdown，别用阮一峰那套语气，不用配脚本。

**Skill 行为**：

0. **意图解析**：
   → 输入形态：提到"我们仓库" → 先读仓库 README 与 `docs/` 既有结构
   → 技术类型：中间件 → 骨架要含数据结构、持久化、集群、缓存典型问题
   → 交付形态：单文件 Markdown，落在 `docs/`，跳过三级目录、README、`_meta.yaml`
   → 语气：不要阮一峰 → 改中性技术写作，短句直述、少类比
   → 内容深度：面试导向 → 每个知识点按「考点 → 常见追问 → 答错点」组织
   → 配套脚本：0，Step 4 跳过
1. 读仓库 README / AGENTS.md / `docs/` 命名，确认单文件放哪、是否要 front-matter。
2. 列 Redis 面试高频清单（数据结构与底层编码、持久化 RDB/AOF、主从与哨兵、Cluster、缓存穿透击穿雪崩、分布式锁），按考点重排。
3. 单文件写完：每节「考点 → 追问 → 答错点」；沿用项目 front-matter；不套「学习重点 ⭐ / 注意」那套标注体系，改用「高频」小标题。
4. **跳过**（用户说不用脚本）。
5. 不跑 `check_tutorial.py`（不是三级目录形态），按人工六项核对后交付。
