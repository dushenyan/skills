# 菜鸟风格技术教程生成器

根据用户给出的技术名称（如 Milvus、FastAPI、LangChain 等），生成一份**循序渐进、通俗易懂、全链路覆盖**的中文技术教程。排版对齐 [菜鸟教程 runoob.com](https://www.runoob.com) 的编辑风格，叙事语气贴近**阮一峰老师**（[ruanyifeng.com](https://www.ruanyifeng.com)），并配套一个**可运行的项目案例**。每章结尾附一句轻量的"下一站建议"，告诉学习者本章看完后最推荐去哪里。

## 一、核心要点速览

> 这一节是硬指标清单。动手前先逐条记住，细节再按需翻 `references/`。

- **阮一峰风格贯穿全文**：问题驱动开头、生活化类比、口语化短句、每章 1~2 处作者视角；严禁学术腔、教材腔、官腔、卖课腔。
- **输出三级目录**：技术名目录 → 按学习阶段分组的子目录 → 中文文件名的章节 Markdown 文件；教程末尾补一篇 README.md。
- **章节按知识点灵活组织**：参考章节是"菜单"不是"清单"。按这门技术的知识点决定取舍、增删与排序，不凑数、不硬套、不留空章。
- **代码必须能直接跑**：完整、自包含、复制即可执行；Python 使用 Google 风格 docstring；行内注释解释"为什么这样做"；每个示例附预期输出。
- **版本**：使用该技术**最新且适合生产环境的稳定版本**，生成前用 WebSearch 确认版本号，并在教程中明确标注。
- **实战项目资源硬约束**：资料优先使用**中文资源与国内可访问数据源**；所有链接成文前必须用 WebFetch **逐个验证可访问**，死链一律替换，禁止编造 URL。
- **正文中文 + 全角标点**（，；：（）。）；代码块、行内代码、URL、命令行参数、配置键值内保持英文标点。
- **Python 环境一律用 `uv`**：`uv init` / `uv add` / `uv run` / `uv lock`，不使用 pip、conda、poetry。
- **每章结尾一句"下一站建议"**：引用块格式、一句话、点名下一章去哪；可跳过的章节明确告知跳过路线。
- **每 2~3 章至少 1 处配图建议**：引用块格式，画面描述要具体可感。（这一条最容易被整章漏掉，别漏。）
- **非必要不使用分割线 `---`**：章节与小节一律靠标题层级自然分隔，**单篇文档**中 `---` 不超过 2 处。

## 二、核心约束（必须严格遵守）

### 1. 版本要求

- **必须使用该技术最新且适合生产环境的稳定版本**（不使用 beta/alpha/已废弃版本）。
- 生成前应通过 WebSearch 确认当前最新稳定版本号，并在教程中明确标注版本（如 `Milvus 2.4.x`）。
- 如该技术版本迭代较快，需注明"本文基于 XXX 版本，后续版本可能有所差异"。

### 2. 包管理工具

- **所有涉及 Python 包管理的场景，一律使用 `uv` 管理**，不使用 pip/conda/poetry。
- 环境初始化、依赖安装、运行脚本均使用 uv 命令。
- 非 Python 技术栈（如 Node.js）使用对应生态的标准工具，但需在教程中说明。

### 3. 代码示例要求

- **所有代码示例必须可直接运行**（完整、自包含，用户复制即可执行）。
- 注释采用 **Google 风格**（Python）或对应语言的通用规范：函数/类用 Google 风格 docstring（Args / Returns / Raises / Example）；行内注释解释"为什么这样做"而非"做了什么"。
- 如某概念无法用真实代码清晰表达，**允许使用伪代码**，但必须标注 `# 伪代码` 并通俗易懂地解释。
- 每个代码示例后附**预期输出**（用注释或代码块标注"输出："）。

### 4. 语言与标点

- 全程使用**中文**撰写。
- 正文中逗号用 `，`、分号用 `；`、冒号用 `：`、括号用 `（）`、句号用 `。`。**严禁在正文混用英文半角标点**。
- 以下内容**不受此规则限制**（必须保持英文标点）：代码块内、行内代码内、URL 链接、命令行参数、配置文件键值。

## 三、按需加载的资料文件

按当前正在做的步骤，读对应的那一份就够，不必全部读进来。

| 文件 | 什么时候读 | 里面有什么 |
|---|---|---|
| `references/narrative-style.md` | **写任何讲解段落之前必读** | 阮一峰风格六大特征、禁用写法清单、风格自检清单、类比规范 |
| `references/tutorial-structure.md` | **规划章节目录时必读**；写章末过渡时查第三节 | 章节组织原则、13 个参考章节菜单、章末"下一站建议"规范、三级输出目录与命名 |
| `references/formatting.md` | 排版时查，配图建议必看第六节 | 标题层级与分割线、四种引用块标注、代码块规范、表格、输出标注、配图提示词 |
| `references/project-case.md` | **写实战项目章节时必读** | 六小节结构（缺一不可）、中文资源来源清单、链接验证要求 |
| `scripts/check_tutorial.py` | 生成完跑一次 | 机械自检：标点、分割线、禁用词、章末指引、配图覆盖、代码块语言标注、文件名 |

## 四、生成流程

**Step 1 · 确认版本**
用 WebSearch 搜索该技术的最新稳定版本号。

**Step 2 · 确认安装方式**
搜索官方文档确认安装方式（Docker / 二进制 / 包管理器）。

**Step 3 · 规划章节目录**
先读 `references/tutorial-structure.md`。以该技术的**知识点为主线**，从参考菜单中取舍、增删、合并，列出实际要写的章节目录（必备骨架不可少），按学习曲线排序并重新编号。不硬凑 13 章。

**Step 4 · 确认实战项目可行性**
搜索该技术的官方 Quickstart 或 Demo 项目，作为实战章节的参考素材。

**Step 5 · 收集中文资源并验证链接**
先读 `references/project-case.md` 的第二节。为实战章节整理中文文档、国内数据集与参考项目链接，用 WebFetch 逐个访问验证，死链替换为可访问的同类中文资源；确无中文资源才用英文官方资源并注明。

**Step 6 · 逐章生成**
- 先读 `references/narrative-style.md`，讲解段落必须贯彻六大特征。
- 排版细节查 `references/formatting.md`；每 2~3 章给一处配图建议。
- 每章结尾（除最后一章）加一行轻量的"下一站建议"引用块，**指向实际存在的下一章**。
- 实战项目章节按 `references/project-case.md` 的六小节写全。

**Step 7 · 跑校验脚本**

```bash
python3 scripts/check_tutorial.py <教程目录>
```

按脚本报告逐条修复。脚本覆盖的是机械项，风格是否到位仍需对照 `references/narrative-style.md` 第三节的自检清单过一遍。

**Step 8 · 补 README.md**
在教程根目录补一篇 README.md，介绍目录结构、依赖安装、项目案例运行方式。

## 五、输出格式

- **三级目录结构**：技术名称目录 → 按学习阶段分组的子目录 → 章节 Markdown 文件。
- 每章文件命名 `<序号>-<中文标题>.md`，序号全局连续，标题取自该文件一级标题。
- **禁止在文件开头添加"参考来源"引用行**，官方资源统一放在最后一章"参考资源"。
- 完整的目录示例、子目录分组逻辑与命名约定见 `references/tutorial-structure.md` 第四节。

## 六、示例对话

**用户**：帮我生成一份 Milvus 的教程，菜鸟风格。

**Skill 行为**：

1. 先 WebSearch 确认 Milvus 最新稳定版本与安装方式。
2. 读 `references/tutorial-structure.md`，以 Milvus 的知识点为主线规划章节目录，不硬凑 13 章。
3. 读 `references/project-case.md`，为实战项目收集中文文档与国内数据集资源，用 WebFetch 逐个验证链接、替换死链。
4. 读 `references/narrative-style.md`，按规划顺序逐章生成，所有讲解贯彻阮一峰风格。
5. 排版按 `references/formatting.md`，每章结尾加一句"下一站建议"指向实际存在的下一章，每 2~3 章给一处配图建议。
6. 所有 Python 示例使用 uv 管理依赖、Google 风格注释。
7. 实战章节按六小节写全（目标与亮点、项目结构、资料准备、完整代码、运行步骤、扩展建议）。
8. 跑 `scripts/check_tutorial.py` 校验并修复；输出为三级目录的 Markdown 文件，中文文件名，章节间不使用分割线。
9. 最后补一篇 README.md，介绍教程目录结构、安装依赖、运行项目案例。
