## 一、标题层级与分割线

- `#` 文档标题，`##` 一级章节，`###` 二级小节，`####` 三级小节。
- **默认不使用分割线 `---`**：章节之间、小节之间一律靠标题层级自然分隔，不在章节末尾追加 `---`。
- 不同操作主题之间用三级标题（`####`）分隔，不用分割线。
- 仅在极少数场景（同一小节内部、代码块与大段文字之间确实需要视觉断点）才偶尔使用，**单篇文档中 `---` 不超过 2 处**；能不用就不用。

标题层级本身就是分隔线。额外再画一条横线，只会让文档显得零碎。

## 二、重点标注

### 1. 五种引用块

四种基础标注 + 一种踩坑变体，各管一类信息：

| 用途 | 格式 | 使用时机 |
|---|---|---|
| 关键概念 | `> **学习重点 ⭐**：` | 必须让读者记住的抽象、机制、原理 |
| 注意事项 | `> **注意**：` | 参数默认值、行为差异、容易忽略的前置条件 |
| 踩坑提醒 | `> **踩坑提醒**：` | 常见的错误现象 + 原因 + 修法，比「注意」更重 |
| 版本说明 | `> **版本说明**：` | API 变动、行为因版本而异 |
| 类比 | `> **类比理解**：` 加粗开头 | 抽象难懂的概念配一个生活化类比 |

### 2. 小标题也要能「扫读定位」

为了让读者跳读时一眼抓到重点，**常见场景**、**基本用法**、**易错点** 这类反复出现的小节标题要统一写法，方便目测：

```markdown
#### 常见场景：按主键批量拉取

#### 基本用法：单次插入

#### 易错点：索引创建后不立即生效
```

同一份教程里同类小节的标题前缀要一致（要么都叫「常见场景」，不要一会儿「典型用法」一会儿「使用场景」）。

### 3. 覆盖度底线

除「参考资源」这种纯链接章外，每一章至少要出现：

- 1 次 `> **学习重点 ⭐**`（讲透一个核心概念时贴上去）
- 1 次 `> **注意**` 或 `> **踩坑提醒**`（哪怕技术简单也要提一个易错点）

`scripts/check_tutorial.py` 会按章统计这两类标注是否缺失，作为 WARN 提醒（不阻断交付）。

## 三、代码块

- **必须标注语言类型**（` ```python `、` ```bash `、` ```yaml ` 等），不要留裸 ` ``` `。
- 关键代码行配**解释性注释**：解释「为什么这么做」，而不是「这行在做什么」。
- 常见 / 高频知识点要给 **2~3 个使用变体**（如：一次性脚本 vs 生产写法、简单配置 vs 高级配置），每个变体一个独立代码块 + 一行说明它的取舍。
- Python 代码使用 Google 风格 docstring：

```python
def example_function(param1: str, param2: int) -> bool:
    """简述函数用途。

    详细说明函数的行为和设计意图。

    Args:
        param1: 参数1的说明。
        param2: 参数2的说明。

    Returns:
        返回值的说明。

    Raises:
        ValueError: 何时抛出异常。

    Example:
        >>> example_function("test", 1)
        True
    """
    # 这里解释为什么这么做，而不是做了什么
    return len(param1) == param2
```

为什么坚持 Google 风格：初学者读 docstring 就是在读"这个函数怎么用"。Args / Returns / Example 三段固定位置，比散文式注释好扫得多。

某个概念实在没法用真实代码说清时，允许用伪代码，但必须在代码块首行标注 `# 伪代码`，并用文字把意图讲明白。

## 四、表格

- 对比类信息一律用表格，表头加粗。
- 表格后必须有文字总结。
- **易混淆概念必用对比表**：维度至少包含「适用场景 / 性能或成本 / 生态与学习曲线」，表后 1~2 段文字给出「什么时候选哪个」的判断依据。

表格只负责摆事实，结论得用文字讲出来。表后没总结，读者得自己归纳，这一步很多人就跳过了。

## 五、输出标注

代码示例后用如下格式标注输出：

```
输出：
（这里展示预期输出）
```

## 六、配图提示词

### 1. 什么时候给

每个章节生成时，主动识别**适合配图的位置**（如架构图、流程图、概念示意图、对比图等），至少每 2~3 个章节给出 1 处配图建议。

> 这一条在实践中最容易被整章跳过。已有的 Milvus 全套 23 章里，配图建议出现 0 次——不是因为它不重要，而是因为它被埋在长文档中间。生成时请把它当成和"下一站建议"同级的必做项，`scripts/check_tutorial.py` 会按"每 3 章至少 1 处"来检查。

### 2. 格式

配图建议用**引用块**标注，格式统一如下，用户可复制"画面描述"交给 ChatGPT / Midjourney 等工具生成：

```
> **配图建议**：
> - 用途：说明 XXX 概念 / 展示 XXX 流程
> - 画面描述：<一段具体的中文画面描述，包含主体、元素关系、视觉风格，可直接用于图片生成>
> - 风格：扁平插画 / 技术线框图 / 等距示意图 / 流程图 / 信息图
> - 尺寸建议：landscape_16_9 / landscape_4_3 / square
```

### 3. 画面描述要具体可感

"画一张架构图"不能用。"左侧三个圆角矩形从上到下排列，代表三种索引类型，每个矩形右侧连出一条箭头指向中央的数据库图标，箭头旁标注索引名，整体使用蓝色系扁平插画风格"才可以用。
