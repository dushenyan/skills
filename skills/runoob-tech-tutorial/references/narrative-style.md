# 叙事风格：阮一峰老师写法规范

> 这是硬性要求，不是建议。所有讲解段落都必须贯彻这套风格。

技术内容可以靠查文档补，风格不能。一篇读起来像教材的教程，读者翻两页就走了；一篇读起来像有人在旁边给你讲的教程，读者会一章一章追下去。这份规范就是后者。

## 一、阮一峰风格的六大特征

### ① 问题驱动，绝不堆砌 API

每讲一个新概念，**先讲"没有它会怎样"**，再讲"它怎么解决"。不要一上来就甩接口列表。

经典句式："如果你想 X，但 Y 很难做到，那么 Z 就是答案。"

- 反例（禁止）：`Z 提供了 a()、b()、c() 三个方法。`
- 正例：`你有没有遇到过这种情况：辛辛苦苦写了一堆代码，结果发现数据查得太慢？Z 就是为了解决这个痛点。`

### ② 从"为什么有这个技术"讲起

简要交代技术**诞生背景**（谁做的、为什么做、解决了什么历史问题）。

涉及知名人物/团队时，可以一句话点出（如"它的作者是某某，写过……"），让读者建立"它不是凭空冒出来的"的认识。

不要写成学术综述，**一两句点到为止**，长篇大论会破坏节奏。

### ③ 口语化短句，绝不绕弯

- **一句话能说清，绝不用两句**。多用句号，少用长从句。
- 主动句优先（"我们启动服务"），少用被动句（"服务被启动"）。
- 多用"你"、"我们"、"我"作为主语，**像跟朋友聊天，不像念稿**。
- 善用"其实"、"不过"、"顺便说一句"、"说到这里"等过渡词，让行文有节奏感。
- 反例：`该方案通过引入抽象层以解耦核心逻辑与外部依赖，从而提升系统的可维护性与扩展性。`
- 正例：`这个方案就是给核心代码和外部依赖中间加一层。这样以后换数据库，就不用改业务代码了。`

### ④ 生活化类比，复杂概念秒懂

每个抽象概念**必须配一个生活化类比**（阮一峰的招牌手法）。类比的三条原则与写法细则见本文第四节。

### ⑤ 偶尔的"个人观察"，拉近距离

在合适的地方插入一句**作者视角的感悟或小趣闻**，但**点到为止**，不喧宾夺主。

不要每段都加，每章最多 1~2 处。句式参考：

- `"第一次看到这个设计时，我愣了一下，没想到可以这么优雅。"`
- `"老实说，我当初也是踩了坑才搞明白的。"`
- `"这里有个细节，官方文档没明说，但我建议你记住。"`

**禁止**使用鸡汤味、煽情、过度的"我们一定要"之类的话。

### ⑥ 结尾留个"钩子"或"小提醒"

每章结尾不要硬邦邦地"本章小结"，而是用一句**温柔的过渡**引出下一章，或留下一个小提醒。

句式参考：

- `"搞懂了这一点，下一章我们就开始动手写代码。"`
- `"如果你之前没接触过 X，先有个印象就行，下一章会展开。"`
- `"这一节可以跳过，等你用到了再回来看。"`

章末过渡的标准格式（"下一站建议"引用块）见 `tutorial-structure.md`。

## 二、禁用写法清单

为了避免破坏阮一峰风格，**严禁出现**以下表达：

| 类别 | 禁用表达 |
|---|---|
| 学术腔 | `综上所述`、`由此可见`、`总而言之`、`本文将详细介绍` |
| 教材腔 | `作为一个 XXX`、`所谓 XXX 就是` |
| 官腔 | `值得我们注意的是`、`需要特别强调的是` |
| 客套腔 | `本教程将带领大家` |
| 过度口语腔 | `小伙伴们`、`老铁们` |
| 卖课腔 | `非常重要！！！`、`必看！！！` |

另外还禁止：

- 连续超过 60 字无标点的长句。
- 没有具体内容的空泛形容（"非常重要"、"极其强大"、"完美解决方案"）。

## 三、风格自检清单

每章生成完毕后，**逐条对照**：

- [ ] 第一句话是不是"问题"或"为什么"，而不是概念定义？
- [ ] 抽象概念有没有配生活化类比？
- [ ] 每段平均句长是否在 30 字以内？
- [ ] 有没有至少一处"作者视角"的轻量表达？
- [ ] 结尾是不是有自然的过渡，而不是"本章小结"？
- [ ] 是否避免了禁用清单中的所有表达？

> 本文第二节的禁用词，以及 `tutorial-structure.md` 第三节的章末过渡，都可以用 `scripts/check_tutorial.py` 自动扫一遍，不用靠肉眼记。句子长度、标点、字间距这类文字层面的规范见本文第五节。

## 四、类比规范（重点强化）

类比是这套风格里最容易被写成"看起来像、其实不成立"的部分，所以单列一节。

### 1. 三条原则

- **贴**：来自读者熟悉的场景（做饭、搬家、图书馆、银行等）。
- **准**：类比核心机制与原概念一致，不要为了形象牺牲准确。
- **短**：一两句话讲完，不展开。

### 2. 标准格式

每个抽象概念都必须配类比（除非确实找不到合适的）。格式统一为：

```markdown
> **类比理解**：用一两句话讲清楚。
```

### 3. 参考示例

> **类比理解**：数据库索引就像书的目录。你不用翻遍整本书，目录能直接告诉你第几页有答案。

> **类比理解**：容器就像一个独立的房间，镜像就是这个房间的"装修图纸"。

为什么值得较真：读者能记住的往往不是 API 名字，而是那个类比。类比错了，后面所有理解都跟着偏。

## 五、阮一峰《中文技术文档的写作规范》核对表

语气之外，文字本身还要过一遍阮一峰的[《中文技术文档的写作规范》](https://github.com/ruanyf/document-style-guide)。**内容生成完毕后必须做这一步**：先跑脚本，再人工过一遍语境项。

下表把规范拆成三类：脚本能判的、本技能有意偏离的、只能人工看的。

### 1. 脚本已覆盖（跑一遍就行）

`python3 scripts/check_tutorial.py <教程目录>` 会把左列逐条扫出来，按「规则名 + 命中处数 + 样例」输出。

| 规范要求 | 脚本规则 | 级别 |
|---|---|---|
| 中文语句一律全角标点 | `正文半角标点` | ERROR |
| 阿拉伯数字一律半角 | `全角数字` | ERROR |
| 感叹号不得连用 | `感叹号连用` | ERROR |
| 省略号用「⋯⋯」，不用 `...`、`。。。` | `省略号写法` | ERROR |
| 括号加注时，句号写在括号外 | `括号内句号` | ERROR |
| 标题末尾不得出现句号、逗号、顿号、分号、冒号 | `标题末尾点号` | ERROR |
| 一级标题下不能直接出现三级标题（禁止跳级） | `标题跳级` | ERROR |
| 半角英数字与全角标点之间不留空格 | `英数字与全角标点间空格` | ERROR |
| 句子构件不超过 40 字 | `句子过长` | ERROR |
| 中文与半角英文之间留一个半角空格 | `中英之间缺空格` | WARN |
| 与中文相邻的数字，加不加空格全文统一 | `数字间距不统一` | WARN |
| 数值过千加千分号 | `千分号` | WARN |
| 尽量不用感叹号 | `正文感叹号` | WARN |
| 省略号不与「等」连用 | `省略号与等连用` | WARN |
| 句子构件 30~39 字需语义明确 | `句长偏长` | WARN |
| 逗号长句不超过 100 字 | `逗号长句过长` | WARN |
| 尽量用主动语态 | `被动语态` | WARN |
| 下级标题不重复上一级标题的名字 | `父子标题同名` | WARN |
| 一个段落不超过 7 行 | `段落过长` | WARN |

脚本报告里 ERROR 级规则命中会让进程以退出码 1 结束，必须改完再交付。

### 2. 规范里有、但本技能有意不遵守的

| 规范要求 | 本技能的做法 | 原因 |
|---|---|---|
| 文件名用半角字符，中文不能用于文件名 | 章节文件用 `<序号>-<中文标题>.md` | 教程面向中文读者，中文文件名在文件管理器里可直接翻找，这是唯一的刻意偏离 |

### 3. 只能人工核对（脚本查不出来）

每章生成完毕后逐条过，宁可慢一遍，也别交一份读起来像机翻的稿子：

- [ ] 长句是否真的拆短了？脚本只卡 40 字上限，30 字的句子读着仍然可能憋气。
- [ ] 被动语态是否改成了主动语态（「数据被写入磁盘」→「数据写入磁盘」）？
- [ ] 是否多用简单句、并列句，少用复合句？
- [ ] 是否用肯定句代替否定句，有没有双重否定？
- [ ] 「的、地、得」是否用对（形容词+的+名词、副词+地+动词、动词+得+副词）？
- [ ] 「其、该、此、这」等代词是否指代明确，只有一个含义？
- [ ] 名词前有没有堆太多形容词，长定语是否拆成了短句？
- [ ] 段落是否一段一个主题，中心句在段首？
- [ ] 英文缩写首次出现时，是否在括号里给了中文标注？
- [ ] 数值变化是否用了「增加了/增加到」「降低了/降低到」，有没有出现「降低 N 倍」这种错法？
- [ ] 全文的人称、语气是否统一（通篇「你」还是通篇「我们」，不要来回跳）？

> 本地如果装有 `ruanyf-document-style-guide` 技能，可以再翻它的 SKILL.md 查细则原文。
