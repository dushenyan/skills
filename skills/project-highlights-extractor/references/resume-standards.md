# 简历改写参考标准

本文件是「项目要点萃取与简历包装」技能的按需参考：改写要点需要选词、寻找量化角度、组织面试故事时读取。它规定**表达口径**（怎么写得像样）；允许补写多少内容见 [packaging-rules.md](packaging-rules.md)，两者不冲突：补的内容照写，但要标 `〔包装·…〕` 并配答辩要点。

---

## 一、Bullet 公式与正反例

### 标准公式

```
动作动词 + 任务/对象 + 方法或技术手段 + 量化结果
```

四要素不必每条俱全，但「结果」位不能空着：要么有数字，要么给保守约数（标包装档），要么留占位符。

### 正反例对照

| 反例（流水账/空话） | 正例（动作 + 手段 + 结果） |
|------|------|
| 负责搜索功能的开发和维护 | 主导 FAQ 语义检索模块开发，设计向量召回 + 精排两阶段链路，Top5 命中率达 92% |
| 优化了接口性能，效果显著 | 重构匹配接口批量查询逻辑，P99 耗时从 800ms 降至 120ms，支撑 QPS 提升 4 倍 |
| 参与项目的测试工作，提高了质量 | 搭建 pytest 接口自动化用例 60+ 条并接入 CI，核心模块回归时间从 2 小时缩短至 10 分钟 |
| 使用 Python、ES、Redis 等技术 | 基于 Elasticsearch + 向量模型实现多知识库隔离检索，服务 3 条业务线、日均调用 50 万次 |
| 解决了线上各种问题 | 定位并修复增量同步漏数问题（binlog 偏移提交时序缺陷），数据一致性校验差异率降为 0 |

### 句式细则

- 长度 30~50 字（约 1~2 行），超过则拆成两条或删掉铺垫。
- 一条只表达一个贡献点；多个成果用分号连接仅限同一动作的直接产物。
- 数字优先于形容词：写「3 倍」「0.05%」，不写「大幅」「极高」。
- 有可信基线但缺精确值时：按 packaging-rules 的量级合理化给保守约数，并标 `〔包装·量级合理化〕`。
- 完全无从推断时（连方向性区间都给不出）才留占位：`搭建 XX 监控告警体系〔待补充：覆盖服务数/告警响应时长〕`。
- 定性事实本身就有说服力，可不配数字：「方案被团队采纳为规范」「零事故运行至今」。

## 二、动作动词词库（按贡献类型分组）

选词原则：动词必须与原文中的实际角色匹配，拿不准就降级一档。

| 贡献类型 | 中文动词 |
|----------|----------|
| 主导/牵头 | 主导、牵头、统筹、规划、发起、从 0 到 1 搭建、拍板 |
| 设计/方案 | 设计、制定、设计并落地、抽象、建模、定义、选型 |
| 开发/交付 | 开发、实现、构建、重构、改造、编写、交付 |
| 优化/攻坚 | 优化、重构、压缩、降低、提升、攻克、定位并修复、治理 |
| 推动/落地 | 推动、推进、落地、引入、推广、促成、驱动 |
| 协作/支持 | 参与、协助、配合、对接、支持、联调 |
| 保障/运维 | 保障、值守、应急、兜底、建立监控、制定预案 |
| 管理/影响 | 带教、评审、组织、协调、主持、沉淀为规范、分享 |

英文简历对应高频词：Led / Designed / Architected / Built / Developed / Refactored / Optimized / Reduced / Increased / Delivered / Drove / Launched / Mentored / Established。

禁用弱开头：负责、进行、参与了……相关工作（除非确实只能证明参与）。

## 三、量化六维清单（找数字的扫描方向）

原文没有直接给指标时，按这六个方向回扫素材找线索：有线索的按 packaging-rules 做量级合理化（标 `〔包装·量级合理化〕`），毫无依据的才转成「补充建议」向用户追问。「追问句式」列同时是面试时对方可能的问法，包装数字也要答得上。

| 维度 | 典型指标 | 追问句式 |
|------|----------|----------|
| 性能 | 响应时间、吞吐量(QPS/TPS)、延迟分位数、启动耗时 | 「优化前后的 P99/P95 分别是多少？峰值 QPS 多少？」 |
| 效率 | 耗时缩短、人力节省、发布频率、自动化率、周转时间 | 「这件事以前多久做一次、花多久？现在呢？」 |
| 成本 | 机器/资源占用、云费用、存储量、带宽 | 「省了几台机器/多少费用？资源利用率变化？」 |
| 质量 | 故障率、缺陷率、命中率/准确率、可用性(SLA)、客诉数 | 「上线前后 bug 数/线上事故/准确率对比？」 |
| 规模 | 用户数、数据量、调用量、接入方数量、覆盖业务线 | 「服务多少用户/多少条业务线？数据量级多大？」 |
| 业务 | 转化率、收入、留存、渗透/覆盖率、交付周期 | 「这个项目对业务指标产生了什么可感知的影响？」 |

数字表达规范：

- 有对比必须带基线：「从 X 降到 Y」「相对 Z 提升 N%」。
- 量级要具体：`50 万次/日` 优于 `大量调用`；`3 节点 ES 集群` 优于 `多台服务器`。
- 换算可以，精度不能编：原文「近一倍」可写成「约 45%」，但不要写成 `47.3%`；包装出的数字一律用整数或约数。
- 同一指标全篇只有一个值，核心要点与 STAR 故事里的数字必须对得上。

## 四、STAR 素材组织标准

第五板块的每个故事按 STAR 组织，总长度控制在 150 字内，面试时可口语展开：

- **S 情境**：业务/系统当时处在什么状况，出现了什么矛盾或瓶颈（1~2 句）。
- **T 任务**：要达成的具体目标是什么，约束条件是什么（时间/资源/兼容性）。
- **行动**：你本人做了什么——排查路径、方案选型、关键技术决策、权衡取舍。这是重点，占一半篇幅；用「先……再……最终……」体现思路。
- **R 结果**：可量化的直接结果 + 可提及的长期影响（沉淀为规范、推广到其他团队）。

选材优先级：有明确数字的硬成果 > 技术难度高/方案有取舍的攻坚 > 体现影响力的机制建设。纯日常开发、无难点无结果的任务不进 STAR 库。

## 五、技术栈深度分级口径

| 等级 | 判定依据（须有原文支撑） | 简历呈现方式 |
|------|--------------------------|--------------|
| 核心使用 | 做过方案设计/选型、核心模块开发、复杂问题排查或性能调优 | 放入「核心使用」，可进核心要点展开 |
| 熟练使用 | 用它完成过常规功能开发，能独立解决一般问题 | 放入「熟练使用」标签 |
| 接触了解 | 仅配合使用、跑通过 demo、项目中出现但非本人操作 | 放入「接触了解」或不写；禁止包装成精通 |

判定争议处理：原文只写「使用 XX 完成……」且任务明显是常规开发，归「熟练使用」；是否升到「核心」取决于有无设计/攻坚证据。

包装补进来的技术（packaging-rules 的手法 2）默认落在「熟练使用」，只有它参与了核心要点句子的主干、且用户讲得清选型理由时，才放进「核心使用」，并在第四板块的「补强项」里注明。

## 六、常见反模式（改写时自查）

1. **职责堆砌**：罗列「负责 A、负责 B、负责 C」，没有动作与结果——按公式重写。
2. **形容词替代数据**：「极大提升」「显著优化」「有力保障」——要么补数字，要么删。
3. **团队成果个人化**：把团队/项目整体数据直接挂在自己名下——补个人动作，或改为「作为成员参与的项目达成……」。
4. **技术名词通货膨胀**：用过就写「精通」，参与过就写「主导」——按深度分级与五档贡献程度如实降级。
5. **一条塞多件事**：一个 bullet 串三个模块——按贡献点拆分。
6. **隐去问题只报喜**：STAR 里没有真实难点，故事失去说服力——保留约束、失败尝试与权衡。
7. **占位符泛滥或缺失**：全文没有一个数据追问，或每条都挂占位符——前者说明回扫不彻底，后者应在补充建议中集中为 3~5 个高价值问题。
8. **包装失控**：一份经历里塞满热门技术、规模量级一路拔高、条目多到用户自己记不住——包装的价值在**可信的密度**，不在数量。每条包装都要答得出追问，答不出的删掉比留着安全。
