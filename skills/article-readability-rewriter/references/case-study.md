# 改写对照案例

案例原文是关于 Function Calling、Tool Use 与 ReAct 的技术讲解。

原稿信息齐全，但开头像教科书宣告，全篇零类比，术语没有实例，核心结论重复五次。

下面四组对照，对应 SKILL.md 里的四个杠杆。

## 案例一：开头（杠杆 1）

原文：

> 面试里常被追问：模型又不能联网，它怎么查天气？如果模型输出了 `search("北京天气")`，到底是谁执行的？
>
> 这就是 `Function Calling`、`Tool Use` 和 `ReAct` 要回答的问题。

改写：

> 模型不能联网，可它偏偏能告诉你明天要不要带伞。
>
> 你以为它偷看了天气。其实它只是写了一张纸条：`get_weather("北京")`。
>
> 真正跑出去查的，是另一个程序。
>
> 这篇文章讲的就是这张纸条，和纸条背后那套循环。

差别：原文用一个问题抛出悬念，紧接着用「这就是要回答的问题」把它掐灭，等于提前收场。改后先给动作，再给名字，读者是被画面带着走的。

## 案例二：类比（杠杆 3）

原文：全篇没有类比，只用「模型不执行，应用执行」反复强调。

改写：

> **打个比方**：你去餐厅吃饭，不能进厨房。你只能在菜单上勾选，服务员把单子送进去，再把菜端出来。
>
> 模型就是那个客人。它永远不进厨房，只负责点菜。`Function Calling` 就是那张菜单——格式固定，厨房不会看错。

价值：一个类比顺手解释了「模型不执行」。后面的章节就不必再重复这句话，省了三段。

## 案例三：术语落地（杠杆 4）

原文：

> 常见形态是模型返回 `tool_calls`。每一项包含调用 ID、函数名、JSON 参数。应用执行后，把结果作为 `tool` 消息回传，并带上 `tool_call_id`。

改写：

```json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\": \"北京\"}"
      }
    }
  ]
}
```

后面接一句点破：

> `tool_call_id` 存在的唯一理由，是让模型知道「这条结果对应我哪次提问」。模型一次可以点好几道菜，没有 ID 就配不上对。

差别：原文把结构描述成四个名词，读者脑中是空的。报文让 `id` 的位置、`arguments` 是字符串这件事，一眼就明白。

## 案例四：结构重排（杠杆 2）

原结构：

1. 具体问题
2. 没有 Function Calling 的年代
3. 概念定义
4. 调用流程
5. ReAct
6. 推理原理
7. 场景与风险
8. 面试话术

问题：读者要读完前三节才第一次看到完整链路。第二节讲历史时，读者还没有画面，不知道「痛点」痛在哪。

改后结构：

1. 具体问题
2. **一次完整调用（先给报文和链路）**
3. 没有它的年代
4. 三个概念的关系
5. ReAct 循环
6. 反直觉点单独成节
7. 推理原理
8. 场景与风险
9. 面试话术

差别：把演示从第四节提到第二节。历史后移，从铺垫变成回顾，读者理解起来轻松得多。

## 这条经验怎么复用

诊断任何一篇文章，都可以问同样四个问题：

- 第一个术语出现前，读者有画面吗？
- 有没有一个能单独转发的实例？
- 最高信息量的一句在哪，是不是埋在列表里？
- 前三节里，有没有可以砍或可以后移的？
