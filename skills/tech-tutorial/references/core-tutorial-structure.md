# 教程结构：章节怎么排、内容怎么讲透、目录怎么建

> 下面参考章节是一份"菜单"，不是必须集齐的"清单"。生成教程时，**以这门技术的知识点为主线**：读者学会这门技术需要经过哪些认知台阶，就排哪些章节；每个台阶都要按「内容深度基线」讲透，不能一句话带过。

## 一、章节组织原则（先读）

1. **按知识点取舍**：技术没有的内容不硬凑。例如，纯前端库不需要"高可用集群"；一个轻量 Python 库不需要"Docker 部署"；命令行工具不需要"前端扩展"。
2. **按知识点新增**：技术特有的重要知识点要敢于加章。例如，ORM 教程要有"数据库迁移"章；状态管理库要有"中间件与插件机制"章；前端框架要有"响应式原理"章。
3. **按学习曲线排序**：总体遵循"是什么 → 为什么用 → 装起来 → 跑通 → 核心概念 → 常用操作 → 实战串讲 → 生产进阶 → 兜底资料"的认知顺序；同类知识点合并，过碎的小节折叠。
4. **编号按实际生成结果重排**：不保留空章、不跳号；每章的"下一站建议"必须指向**实际存在**的下一章。
5. **必备骨架**（缺了教程不完整）：教程总览、技术介绍（是什么）、环境安装、快速开始、基础操作、实战项目、参考资源。
6. **按需选用**：目标读者与前置知识可并入总览；选型对比、核心概念详解、进阶应用、FAQ 视技术复杂度决定有无。
7. **章数不硬凑也不刻意压缩**：常见、高频、易错的知识点要给足篇幅，必要时把一个大学科拆成多章；反之，冷门又简单的知识点合并到相关章节即可。

已有的 Milvus 教程排了 23 章，LangChain 排了 22 章，都远超参考项——这是正常的。参考项是"考虑过再决定要不要"，不是"照着填"。

## 二、内容深度基线（六要素，写作时对照）

> 这是让教程「更丰富、重点突出」的核心约束。每一节正文在讲一个知识点时，都要按下面六个要素讲透，缺一项就是没写完。

### 六要素清单

| # | 要素 | 至少给到什么 |
|---|---|---|
| 1 | **是什么** | 一句话定义 + 一到两句补充（谁做的、解决什么问题）。 |
| 2 | **为什么需要** | 讲痛点：没有它会怎样、别的方案为什么不够用。至少 2~3 句。 |
| 3 | **基本用法** | 最小可运行代码 + 预期输出 + 关键行注释。 |
| 4 | **常见场景 / 变体** | **至少 2~3 个**使用变体或真实场景（如：一次性脚本 vs 生产环境、简单配置 vs 高级配置、单表 vs 关联查询）。每个变体给代码或参数说明。 |
| 5 | **易踩的坑 / 注意** | 常见错误、性能陷阱、版本差异、参数默认值等，用 `> 注意` 单独成块。 |
| 6 | **一句话小结 / 下一站** | 一句话回扣本节，再接章末「下一站建议」。 |

### 重点突出机制

- **核心概念**：用 `> 学习重点 ⭐` 单独成块，让读者一眼看到必须记住的抽象。
- **常见场景**：小标题用 `#### 常见场景：<一句话场景>` 起手，读者跳读时能定位。
- **易错点**：`> 注意` 或 `> **踩坑提醒**` 单独成块，紧跟在出问题的代码之后。
- **易混淆概念**：一律用对比表 + 表后 1~2 段文字总结"什么时候选哪个"。
- **可运行示例**：全篇写完后，挑 2~5 个最重要、最能建立手感的示例抽成编号脚本落到 `~/Desktop/engineering_examples/<主题>/`（约定见 `feature-code-examples.md`），正文对应小节末尾标注脚本路径，让读者能从"读"跳到"跑"。

### 判断是否讲透的一把尺

**读完这一段，读者能不能独立把它用起来？** 如果不能——多半缺了"常见场景"或"坑"；如果能——不要再写"补充说明"凑篇幅。

### 每章的最小覆盖

- **必备骨架章**（技术介绍、环境安装、快速开始、基础操作、实战项目、参考资源）：至少出现 1 处 `> 学习重点 ⭐` 与 1 处 `> 注意`。
- **按需章**（选型对比、核心概念详解、进阶应用、FAQ）：按知识密度决定；FAQ 章每个问题按"现象 → 原因 → 解决"三件套讲完。

`scripts/check_tutorial.py` 会统计每章是否出现「学习重点 / 注意」标注，作为 WARN 提醒。

## 三、参考章节菜单

每项标注了【必备】/【按需】。**必备骨架不能少，按需章节看技术决定。** 每个章节内部按第二节「内容深度基线」的六要素展开。

### 参考章节 1：教程总览（XX 教程）【必备】

- 一句话定义该技术是什么、做什么。
- 1~2 段通俗介绍（谁开发的、用在哪些领域、为什么流行）。
- 目标读者、前置知识较短时，直接并入本章，不必单独立章。

> 下一站建议：接着翻《谁适合阅读本教程？》，判断一下自己是不是目标读者。

### 参考章节 2：谁适合阅读本教程？【按需，可并入总览】

- 明确目标读者（如后端开发、数据工程师、AI 应用开发者）。

> 下一站建议：接着翻《阅读本教程前，您需要了解的知识》，把前置短板补一补。已经熟悉的可直接跳到《XX 是什么？》。

### 参考章节 3：阅读本教程前，您需要了解的知识【按需，可并入总览】

- 列出前置知识（编程基础、相关概念等），并给出学习链接建议。

> 下一站建议：接着翻《XX 是什么？》，正式认识这门技术。

### 参考章节 4：XX 是什么？【必备】

- 通俗解释技术本质。
- 列出**核心特性**（用列表 + 简要说明）。
- 如适用，补充**核心概念**（用 `> 学习重点 ⭐` 标注关键抽象）。

> 下一站建议：接着翻《环境准备与安装》，开始动手。如果你想先做选型，可以先看《为什么选择 XX？》。

### 参考章节 5：为什么选择 XX？（与其他方案对比）【按需，选型向读者必读】

- 用**对比表格**展示该技术 vs 同类方案（如 Milvus vs Pinecone vs Weaviate）。
- 表格维度：性能、易用性、部署方式、社区生态、适用场景等。
- 表格后用 1~2 段文字总结"什么场景选它"。

> 下一站建议：选型决策章节，做技术选型的朋友建议读一读；纯使用者可以直接跳到《环境准备与安装》。

### 参考章节 6：环境准备与安装【必备】

- **使用 uv 进行 Python 环境管理**（非 Python 技术用对应工具）。
- 步骤化：系统要求 → 安装运行时 → 初始化项目 → 安装依赖。
- 每步给出可执行命令 + 预期输出。
- 如需 Docker，给出 docker-compose 或 docker run 命令；技术本身不需要容器部署则不写。

> 下一站建议：环境装好后，翻到《快速开始（Hello World）》，跑通第一个程序。

### 参考章节 7：快速开始（Hello World）【必备】

- 最小可运行示例，让用户 5 分钟内跑通第一个程序。
- 代码完整、注释清晰、附输出结果。
- 代码使用 **Google 风格 docstring**。

> 下一站建议：跑通了 Hello World 信心就有了。下一站翻《基础操作教程》，把会用到的操作一个个过一遍。

### 参考章节 8：核心概念详解【按需，概念密集的技术才独立成章】

- 逐个讲解核心技术概念（每个概念一个小节）。
- 每个概念：定义 → 特点 → 类比理解 → 代码示例。
- 概念间关系用文字或简单图示说明。
- 概念较少时，本章拆散并入《基础操作教程》对应小节即可，不必硬立一章。

> 下一站建议：这章更像概念字典，第一次可以快速浏览建立索引。需要动手时再翻《基础操作教程》边做边查。

### 参考章节 9：基础操作教程（循序渐进）【必备】

- 按学习曲线由浅入深编排操作教程。
- 每个操作：说明 → 代码示例 → 输出 → 解释。
- 不同操作主题之间用**三级标题**分隔，不使用分割线。

> 下一站建议：基本功打好了。下一站翻《实战项目案例》，把零散的知识点串成一个能跑的项目。

### 参考章节 10：实战项目案例（端到端 Demo）【必备】

- 目的：让学习者通过**一个完整可运行的项目**，把零散知识点串起来，亲手触摸该技术的**重点与亮点**。

本章细则（六个小节齐全、资源怎么选、链接怎么验）见 `feature-project-case.md`。

> 下一站建议：把项目跑起来并且自己改一改，是这一步最值钱的收获。下一站翻《进阶应用》，了解这门技术在生产环境里要关心什么。

### 参考章节 11：进阶应用【按需】

- 生产环境相关主题：性能优化、高可用、安全配置、监控等。技术本身不涉及的主题不写。
- 最佳实践建议。

> 下一站建议：进阶内容通常需要结合实际场景看。如果当前还在学习阶段，可以先翻《常见问题与避坑指南》查一查常踩的坑。

### 参考章节 12：常见问题与避坑指南【按需】

- 列出初学者常踩的坑及解决方案。
- 用 Q&A 格式或"问题 → 原因 → 解决方案"格式。

> 下一站建议：FAQ 不必通读，收藏备用。遇到具体问题时再来翻《参考资源》找官方资料。

### 参考章节 13：参考资源【必备】

按四类分组，顺序固定：

1. **官方与文档**：官网、官方文档（优先中文文档链接）、版本发布说明。
2. **代码与社区**：官方仓库、示例仓库、问答社区、中文论坛。
3. **视频课程**：见下方细则，**国内与国外平台都要有，且必须汲取内容反哺正文**。
4. **延伸阅读**（可选）：书籍、系列博客、会议演讲。

所有链接都要验证可访问。视频链接同样不能凭印象写；视频还必须拆出内容写回正文，不能只当链接陈列。

#### 视频资源与反哺要求（硬规则）

**数量与分布**：3~6 条，其中**国内平台不少于 2 条、国外平台不少于 2 条**。只列 B 站不列 YouTube，或反过来，都算不合格——读者的网络条件不同，只给一边等于断了一半人的路。

| 来源 | 常见平台 |
|---|---|
| 国内 | B 站、中国大学 MOOC、慕课网、极客时间、阿里云开发者社区、腾讯课堂 |
| 国外 | YouTube、Coursera、edX、Udemy、freeCodeCamp、官方大会频道 |

**每条视频给五项信息**：

- 标题（原题，不要自己改写）
- 平台与链接（已验证可访问）
- 时长（长课标总时长，单集标单集时长）
- 语言与字幕（中文 / 英文 / 英文配中字）
- 适合阶段（入门 / 进阶 / 专题）

**内容汲取清单（每条视频至少记这些）**：

| 项目 | 要记什么 | 写回哪里 |
|---|---|---|
| 时间锚点 | 视频演示到哪一步 | 参考资源章的映射表 |
| 实操动作 | 安装、配置、快捷键、布局、命令、点击路径 | 对应的上手 / 基础操作 / 实战章 |
| 判断标准 | 视频里怎么算成功、怎么算失败 | 对应章的验收标准或判定表 |
| 坑与前置条件 | 版本差异、系统权限、外层快捷键冲突 | 对应章的 `> 注意` |
| 取舍理由 | 视频为什么这么做 | 对应章的解释段 |
| 不要照抄 | 特定环境、花哨演示、已过时配置 | 映射表的「不要照抄」列 |

**反哺流程**：

1. Step 1 先逐条打开公开页面，按上面的清单记成「视频 → 教程」映射表。
2. 排目录时，把每条视频的实操动作分配到最该出现的章节，而不是统一堆到参考资源章。
3. 写正文时，把视频里的动作改写成读者能跟着做的步骤、命令、判定标准和注意块。
4. 参考资源章保留映射表，让读者看完视频后知道该回哪一章动手。
5. 拿不到字幕或正文时，在映射表注明依据来自公开简介、章节标题或配套文字笔记；不要编造逐帧细节。

**映射表格式**：

```markdown
| 视频时间 | 视频里在做什么 | 教程落点 | 你要做出来的东西 | 不要照抄的部分 |
|---|---|---|---|---|
| 0:14 | 安装并验证 | 安装章 | 能打印版本号 | 具体安装命令按本机环境改 |
```

**丰富度下限**：用户说「越丰富越好」时，每个视频至少反哺一处正文实操；同一主题的视频合并成更完整的「按视频做一次」小节，不要散成一句提示。能把视频里的演示拆成「先手动跑一遍 → 按视频做一次 → 什么时候不该这么做」三层，优先这样写。

**选取标准**：

- 优先官方出品或官方大会演讲，其次高播放高口碑的系统课。
- 优先「成套」而不是「零散切片」，读者要的是能跟着走完的路径。
- 尽量覆盖不同形态：一条快速入门、一条系统精讲、一条实战或专题。

**不可达链接的处理**：

YouTube 等境外平台在国内可能打不开。收录境外视频时，同一条目的备注里写清语言与字幕情况，并确保国内视频条目足以独立支撑学习；反过来，只依赖国内平台时，也要补官方英文原始课程，方便读者核对外文资料。

**视频链接表格式**：

```markdown
| 标题 | 平台 | 时长 | 语言 | 适合阶段 |
|---|---|---|---|---|
| 【官方】XXX 快速入门 | B 站 | 1 小时 20 分 | 中文 | 入门 |
| XXX Full Course | YouTube | 6 小时 | 英文，无字幕 | 系统精讲 |
```

> 教程到这里就结束了。建议把这份教程当作"地图"：用到了再回来翻对应章节，不必从头再来。

## 四、章末"下一站建议"规范

**每个章节（除最后一章外）正文结束后，必须在最后一行加一个引用块**，作为本章与下一章之间的轻量过渡。

格式统一为：

```markdown
> 下一站建议：<一句话，告诉学习者本章看完后最推荐去哪里，可以跳、可以回头读，但不啰嗦>。
```

要求：

- **只用一句话**，不超过 30 字。
- 语气温柔自然，**不写"必看"、"必读"、"重要通知"等重语气**。
- 必须告诉学习者**接下来看哪一章最合适**（写实际章名），而不是空泛地说"继续学习"。
- 对**可选跳跃章节**（如选型对比、概念详解、进阶应用、FAQ），明确告知可以跳过，并给出另一条路。
- 最后一章（参考资源）改用收尾式指引：

> 教程到这里就结束了。建议把这份教程当作"地图"：用到了再回来翻对应章节，不必从头再来。

为什么这一条要单独强调：教程最大的流失点不是内容不够，而是读者**不知道该往哪走**。一句话的指引，比一整段"本章小结"有用得多。

可用 `scripts/check_tutorial.py` 批量检查每一章是否漏了这句。

## 五、输出目录结构

### 1. 三级目录

教程组织为**三级目录**，层级关系为：技术名称目录 → 按学习阶段分组的子目录 → 章节文章文件。

以下为**章节齐全时的示例结构**；实际章节按第一节原则依知识点增减，子目录分组与文件编号随之调整：

```
Milvus教程/                          # 第一级目录：技术名称
├── 01-入门指南/                    # 第二级：学习阶段子目录
│   ├── 01-Milvus教程.md            # 第三级：章节文件
│   ├── 02-谁适合阅读本教程.md
│   ├── 03-阅读本教程前需要了解的知识.md
│   └── 04-Milvus是什么.md
├── 02-核心原理/
│   ├── 05-为什么选择Milvus.md
│   ├── 06-环境准备与安装.md
│   └── 07-快速开始.md
├── 03-实战与进阶/
│   ├── 08-核心概念详解.md
│   ├── 09-基础操作教程.md
│   ├── 10-实战项目案例.md
│   └── 11-进阶应用.md
└── 04-收尾/
    ├── 12-常见问题与避坑指南.md
    └── 13-参考资源.md
```

### 2. 子目录分组逻辑

子目录名与分组可按实际章节调整，常见分法：

| 子目录 | 装什么 |
|---|---|
| `01-入门指南` | 教程总览、目标读者、前置知识、技术介绍 |
| `02-核心原理`（或 `02-上手实践`） | 选型对比（按需）、环境安装、Hello World |
| `03-实战与进阶` | 核心概念（按需）、基础操作、实战项目、进阶应用（按需） |
| `04-收尾` | FAQ（按需）、参考资源 |

实际产出会是这个样子——主题足够大时，子目录按知识专题再拆细：

```
Milvus/                    LangChain/
├── 01-基础教程/            ├── 01-基础教程/
├── 02-核心概念/            ├── 02-核心概念/
├── 03-集合管理/            ├── 03-基础操作/
├── 04-搜索与查询/          ├── 04-实战项目/
├── 05-进阶应用/            ├── 05-LangGraph专题/
├── 06-参考资源/            ├── 06-进阶应用/
└── README.md               ├── 07-LangSmith专题/
                            ├── 08-参考资源/
                            └── README.md
```

### 3. 文件命名与内容约定

- 生成的教程保存为 Markdown 文件。
- **文件命名必须使用中文**：`<序号>-<中文标题>.md`（如 `01-Milvus教程.md`、`02-谁适合阅读本教程.md`）。标题取自该文件的一级标题（去掉序号前缀后的部分），不要用英文或拼音。
- 实战项目章节的文件名按实际编号命名（如 `09-实战项目案例.md`），并在文件开头提供项目代码下载链接（Gitee/GitHub 仓库或 Gist）或完整代码内嵌。
- 如教程较长，可拆分为多个文件，按 `01-xxx.md`、`02-xxx.md` 编号，并在首个文件提供目录索引。
- **禁止在文件开头添加"参考来源"引用行**（如 `> 参考: [官方文档](url)`）。官方资源统一放在最后一个章节"参考资源"中列出即可，文件正文直接从一级标题开始。
- 教程末尾补一篇 `README.md`，介绍目录结构、依赖安装、项目案例运行方式。

### 4. `_meta.yaml` 目录树清单（教程根目录必备）

教程根目录同时生成一个 `_meta.yaml`，供知识库前端渲染导航树。**文件节点**带随机且不重复的 UUID，**目录节点**只用 `children` 嵌套表示层级、不带 `id`；根节点 `name` 是教程名的 kebab-case。

```yaml
# Milvus 教程目录树
# 文件节点带随机且不重复的 UUID，目录节点以 children 嵌套表示层级

name: milvus
children:
  - name: README.md
    id: 501cc5b3-f5af-48c2-9878-a10e7bff030f
  - name: 01-入门指南
    children:
      - name: 01-Milvus教程.md
        id: ef5f4ca7-830f-434c-91d1-347bdb4f480c
      - name: 02-谁适合阅读本教程.md
        id: 36b46079-af0c-4dad-aaec-35c568447c1b
```

约定：

- 注释头两行照上面模板写：第一行 `<教程名> 教程目录树`，第二行说明 UUID 约定。
- 节点顺序与磁盘一致：`README.md` 排最前，目录按编号升序，目录内文件按序号升序。
- UUID 用 `uuidgen` 或等价方式生成小写标准格式，全文件内不得重复；目录节点绝不写 `id`。
- 根 `name` 取教程目录名转 kebab-case（如 `Milvus教程` → `milvus`，`HarnessEngineering` → `harness-engineering`）。
- 后补/重命名章节文件时要同步维护该文件。
- `scripts/check_tutorial.py` 会校验树与实际文件是否一致（WARN）。
