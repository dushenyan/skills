# 论文解读与笔记生成器

默认产出是阮一峰风格的深度解读文章；换任务类型或语气时按第七节第 0 步拨动。

本 Skill 用于把用户给出的一篇论文或技术长文（PDF / 链接 / 标题皆可），变成一份**中文可读材料**——默认是一篇通俗、好读、有观点的深度解读文章，也可以按用户要求做成精读笔记、一页纸摘要、汇报稿或对比综述。

默认手法：叙事语气与排版**直接复用 `ruanyf-document-style-guide` 技能**，结构走第五节的骨架菜单。

**排版与中文写作风格不在本文件维护。** 生成前加载 `ruanyf-document-style-guide`，按它的核心速查与 `core-narrative-style` 执行；本文件只补充论文解读特有的规则：公式处理、原文引用、元信息块、结构骨架与 5 点收尾。

**默认手法整体可覆盖。** 用户如果点明了任务类型、读者、篇幅、语气、章节结构、公式处理或输出落位，以用户要求为准——不要拿阮一峰风格和八段式去顶撞用户。第七节第 0 步专门处理这件事。

## 一、核心要点速览（生成前先读这一节）

> 这一节是**默认稿**（深度解读文章）的硬指标。用户换任务类型或语气后按下表拨动；后面各章只是对它的展开。

- **先讲“为什么”，再讲“是什么”**：任何新概念出现前，先交代它要解决什么痛点。绝不一上来就甩定义、甩公式。
- **零基础也能读懂**（默认读者画像）：假设读者是懂一点编程、但完全没接触过这篇论文的人。每个抽象概念都配一个生活化类比。用户指定了别的读者（研究者、决策者）时，按该读者调整术语深度与类比密度。
- **公式默认逐块拆解**：论文里的核心公式不能直接贴出来就完事，要一层一层拆开讲，每个符号都说明白“它在干什么”。用户要求只给结论、或论文本身不含公式时，不硬造。
- **保留原文出处**：文章开头用引用块列出论文原文链接、作者、发表场合、地位，并在正文引用原句时用引用块标出（可附一句“翻译成人话”）。
- **结尾默认给“背不下来时记这 5 点”**：用编号列表把全文压成 5 条以内。用户明确不要时省略。
- **排版与标点**：按 `ruanyf-document-style-guide` 的硬规则执行（中英文之间加半角空格、正文全角标点、不用 `---` 分隔章节等），本文件不重复列。
- **体量默认约 350～400 行**：讲透，但不注水。宁可砍掉次要章节，也不凑字数。用户要一页纸或万字长文时按用户要求。

以上全部服务于**默认稿**。用户要的是精读笔记、摘要卡片、汇报稿、对比综述、翻译或复现指南时，以第七节第 0 步的任务画像为准，不强行套解读文章的全部约束。

## 二、何时触发

用户出现以下意图时调用：

- “帮我解读/精读/讲解这篇论文”
- 给出一篇 PDF、一个 arXiv 链接、或一个技术长文链接，要求“讲清楚”
- “把这篇 paper 变成人话”“写一篇论文解读”

**硬规则：先头脑风暴，再动笔**。以下两种情况，**必须**先调用 clarify 技能（按技能名加载），没有任何例外：

1. **用户明确要求头脑风暴**——说出“头脑风暴”“brainstorm”“先别写，我们聊聊”“帮我梳理一下思路”等意图时，无论需求看起来多具体，都先调用 clarify 走完澄清流程，用户确认后才进入本技能的写作。
2. **用户给的是模糊表述**——不是具体论文材料，而是一句简短的直接表述或提问（如“语义检索是什么时候？”“讲讲 RAG 吧”），对象、范围都还没定。此时先调用 clarify 进行头脑风暴式澄清（要解读哪篇/哪几篇论文、读者水平、侧重面等），拿到确认后再写作。

禁止拿着模糊表述或未经头脑风暴确认的需求直接猜一篇论文开写。用户明确说「直接做」「不用问」「按你的判断来」时，跳过 clarify，把假设写进交付说明即可。

反触发：用户只是要摘要、要翻译、要列参考文献、要对比多篇论文的表格——这些不是“解读文章”，但**可以用本 Skill 的非默认任务类型承接**（摘要卡片、翻译、对比综述），按用户具体要求走第七节第 0 步的画像，而不是拒答。

## 三、核心约束

> 这一节对**所有任务类型**都成立：先拿全文、元信息准确、引用可追溯、公式定界符合法。排版与语言的完整规则在 `ruanyf-document-style-guide`，这里只列论文解读特有的约束。

### 1. 先拿到全文，再动笔

- 用户给链接：用 WebFetch 抓取正文，**尽量抓全**（各级标题、关键段落、图表说明、附录）。抓不全就在文中诚实说明“原文此部分未获取到”。
- 用户给 PDF：用可用的 PDF 工具读全文，重点抓摘要、引言、方法、实验、结论、附录。
- 用户只给标题：先用 WebSearch 找到原文（优先 arXiv / 官方博客 / 期刊），抓全文后再写。
- **严禁凭记忆编造论文内容**。数字、指标、结论、作者名一律以抓到的原文为准；拿不准的就不写。

### 2. 元信息块必须准确

文章开头固定用引用块给出（字段按论文实际情况增减，宁可少写不可写错）：

```
> **论文**：[《标题》中文翻译版](相对或绝对链接)
>
> **原文**：[英文原文/官方链接](链接)
>
> **作者**：（作者名，机构）
>
> **发表**：（年份，会议/期刊；如果是博文就写“官方工程博客”）
>
> **地位**：（一句话点出它在领域里的位置，这是全篇的“钩子”）
```

- 链接**必须验证可访问**，死链一律替换或删掉，禁止编造 URL。
- **地位**这一栏是全文的悬念所在，要写得有分量但不吹牛。写法：它解决了什么长期问题 × 此后什么因它而变。示例：「现代大模型时代的创世论文」（ML 论文）/「此后所有浏览器都内置了它」（工程文章）——按材料所在领域现写，不套示例。

### 3. 引用原文的方式

引用论文原句时，用引用块，并紧跟一句“翻译成人话”：

```
> 原文：多头注意力允许模型在不同位置联合关注来自不同表示子空间的信息。
>
> 翻译成人话：8 个头可以各学各的，分工干活。
```

不要大段粘贴原文，一段引用不超过三四行。

### 4. 公式处理

定界符只有 `$...$` 与 `$$...$$` 两种；核心公式必须逐块拆解、关键符号给中文解释；写完后过一遍显示自检（配对、转义、空格）。完整规则与示例见 [core-formula-rules](references/core-formula-rules.md)。

### 5. 语言与标点

按 `ruanyf-document-style-guide` 执行。论文解读只额外要求一点：**引用原文时保持英文原样，不改造原文的标点**。

### 6. 示例的使用方式

本技能（含 references）里的所有具体示例——类比、正反例、对比维度、标题句式——都是**方法演示，不是素材库**：

- 演示的是「怎么构造」，实际使用时按同样的方法为当前材料**现做**。
- 禁止把示例内容搬运到无关材料上（解读数据库论文时套 QKV 类比、引用多头注意力的句子，都是错的）。
- 示例多绑定 ML 语境只是演示载体；处理 RFC、官方文档、教材章节时，方法完全相同，素材按领域等价构造。

## 四、叙事风格（默认稿）

完整规则在 `ruanyf-document-style-guide` 的 `core-narrative-style`（含口语化短句、禁用腔调清单等），生成前加载；论文解读特有的四条——先讲为什么再讲是什么、生活化类比（贴/准/短）、偶尔的作者视角、结尾记忆钩子——连同自检清单在 [feature-narrative-rules](references/feature-narrative-rules.md)，逐章撰写时读取。

用户指定了别的语气（严谨学术、工程简报、纯笔记）时，四条整套让位给用户的风格；但「不写空话」与「一句话说清」两条底线始终成立。

## 五、结构骨架（按论文类型选）

> 结构是为了讲清内容，不是为了填满模板。**先判断论文属于哪一类，再选骨架**；用户指定了章节就直接照用户的，不套任何骨架。

| 论文类型 | 怎么认 | 推荐骨架 |
|---|---|---|
| 架构 / 方法创新型（提出新模型、新机制） | 有明确的核心贡献模块，常带公式与架构图 | 骨架 A（八段式，默认） |
| 实验实证型（验证某个假设 / 评测某个做法） | 主体是实验设计、对比与消融，没有新架构 | 骨架 B |
| 理论证明型（定理、收敛性、复杂度） | 核心是定理陈述与证明链 | 骨架 C |
| 综述 / survey | 没有单一核心贡献，按分类梳理整个领域 | 骨架 D |
| 工程博客 / 技术长文（无公式） | 官方博客、实践总结、方法论文章 | 骨架 E |
| 数据集 / 基准型 | 核心资产是数据集或评测基准 | 骨架 F |

## 六、写作细则

标题层级、加粗频率、表格排版等通用项按 `ruanyf-document-style-guide` 执行。论文解读只补充下面三条。

### 1. 章节编号
- `##` 章节用中文序号“一、二、三”，`###` 小节用“3.1、3.2”编号，层级不跳。
- 同级只有一个子标题时并入父级，不留孤立编号。

### 2. 公式与表格
- 公式按 [core-formula-rules](references/core-formula-rules.md) 处理（定界符、逐块拆解、显示自检）。
- 对比类信息用表格，表后必须跟文字总结。

### 3. 配图建议（可选）
如果某处确实需要一张架构图/流程图，用引用块给出配图建议，方便用户交给图片工具生成：

```
> **配图建议**：
> - 用途：说明 XXX 流程
> - 画面描述：<具体的中文画面描述>
> - 风格：技术线框图 / 等距示意图 / 流程图
```

整篇不要超过 2～3 处，能文字讲清的就不用图。

## 七、生成流程

0. **先定任务画像**：动笔前先解析用户这次到底要什么，别默认就写一篇八段式解读文章。

| 画像项 | 可选值 | 影响 |
|---|---|---|
| 任务类型 | 深度解读文章（默认）/ 精读笔记 / 一页纸摘要 / 组会汇报稿 / 多篇对比综述 / 全文翻译 / 复现指南 | 决定结构、篇幅、要不要类比与公式拆解 |
| 读者 | 零基础（默认）/ 同领域研究者 / 决策者 | 决定术语深度与类比密度 |
| 篇幅 | 约 350～400 行（默认）/ 一页纸 / 万字长文 | 决定章节数与每节展开度 |
| 语气 | 阮一峰式（默认）/ 严谨学术 / 工程简报 / 口语讲解 / 纯笔记 | 决定是否适用第四节禁用清单 |
| 结构 | 按论文类型选骨架（默认）/ 用户指定章节 | 见第五节 |
| 公式 | 逐块拆解（默认）/ 保留原样 / 只提结论 | 决定公式处理量 |
| 输出形态与落位 | 单 Markdown 存 `technicals/Papers/`（默认）/ 用户指定目录、文件名、格式 | 见第八节 |

用户没说的一律用默认值；用户说了的记进方案直接执行，**不要停下来问**（除非触发下面的 clarify 条件）。

- 用户要求头脑风暴或给的是模糊表述（如“语义检索是什么时候？”）→ **必须**先调用 clarify 技能澄清（确认要解读的论文、读者、侧重面），拿到确认的重述卡片后再回到第 1 步。
- 具体论文且无头脑风暴要求 → 直接进入第 1 步。
1. **取全文**：按第三章第 1 节抓取论文全文（WebFetch / 读 PDF / WebSearch + WebFetch）。
2. **提炼骨架**：列出论文的摘要、核心贡献（一般 1～3 条）、方法要点、实验结论、局限性。
3. **定“地位”**：用一句话概括这篇论文在领域里的位置，作为元信息块和开篇的钩子。
4. **规划结构**：按第五节骨架菜单选骨架（用户指定章节则照用户的），再按论文实际内容取舍、增删，重新编号，不留空章。
5. **设计类比**（默认解读稿才需要）：为核心概念各想一个“贴、准、短”的类比。摘要卡片与精读笔记可跳过。
6. **逐章撰写**：默认语气下贯彻 [feature-narrative-rules](references/feature-narrative-rules.md) 的四条，用户换了语气按用户的；公式按画像决定是否拆解；引用原文时加“翻译成人话”（笔记与摘要可省）。
7. **写 5 点总结**（默认解读稿才需要）：把全文压成 5 条以内。精读笔记、摘要卡片按各自模板收尾。
8. **自检**：链接与**公式显示**按 [core-formula-rules](references/core-formula-rules.md) 核对；排版与通用风格按 `ruanyf-document-style-guide` 的清单过一遍；论文解读特有项按 [feature-narrative-rules](references/feature-narrative-rules.md) 的自检清单核对。
9. **收尾交付**：保存文件后，按第八章「对话收尾」在对话里简要汇报并附问题选项。

## 八、输出格式

以下是**默认形态**（深度解读文章），用户指定了目录、文件名或格式时以用户为准。

- 文件头的 front-matter（`id` / `title` / `createTime`）按 `ruanyf-document-style-guide` 的输出规范补；它与正文开头的元信息引用块是两回事，都要有。
- 输出为**单个 Markdown 文件**，存放在论文所在目录（默认 `technicals/Papers/`）。当前仓库没有这个目录时，落在工作区根目录并说明一句。
- 文件命名：`<论文标题> 解读.md`。非解读产物按任务类型命名：`<标题> 摘要.md`、`<标题> 精读笔记.md`、`<标题> 组会汇报.md`、`<主题> 多篇综述.md`。
- 若标题含 `:` `/` 等不适合做文件名的字符，用空格或 `-` 替换。
- 文件名沿用仓库现有的中文命名习惯，不使用拼音。
- 用户指定了目录，或要 PDF / HTML / 飞书文档时，按用户要求的形态产出，不必强行写成 Markdown 文件。
- **禁止在文件开头添加“本文件由 AI 生成”之类的声明**，正文从元信息块直接开始（精读笔记可省略元信息块）。

**对话收尾（硬性）**：文件写完后，在对话里的汇总必须以**带编号的问题选项**结尾，让用户直接选下一步。汇报本身一两句话即可（文件路径 + 一句话说明），选项要具体可操作。示例：

```
解读已写好：technicals/Papers/RAG 论文解读.md（约 200 行，含公式逐块拆解与 5 点总结）。

接下来可以：
1. 深入某一章再展开（如“两种 RAG 变体的区别”）
2. 调整类比或侧重面，换个讲法
3. 检查并修正所有数学公式的显示
4. 按同样格式解读另一篇论文
```

禁止用“写好了！这篇解读走的是‘两者结合’路线：”这类自我点评式说辞收尾——不要替用户总结“路线”，把选择权交回给用户。
